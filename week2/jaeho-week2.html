전체 구조 & Networking Model

🎯 이 챕터를 끝내면: 클러스터 네트워킹이 '관리 경로'와 '접근 경로' 두 갈래로 나뉜다는 큰 그림 파악

  • kubelet / CRI / CNI — Pod 생성 및 네트워크 연결
  • kube-proxy / Service — 생성된 Pod로의 트래픽 전달

①Control Plane 경로 — 클러스터 관리

  • 대상: kubectl apply, kubectl get pods, kubectl delete 등 클러스터 상태 조회·변경 명령
  • 핵심 개념: API Server = Kubernetes 관리 요청의 중심 진입점
  • 목적: 애플리케이션 사용이 아닌 클러스터 상태 조회·변경
API Server → Scheduler → kubelet → CRI → Container Runtime → Pod 생성

②Service / Data Plane 경로 — 애플리케이션 접근

  • 대상: Kubernetes 위에서 실행 중인 애플리케이션(Pod)에 대한 접속 요청
  • 핵심 개념: Service = 애플리케이션(Pod)에 접근하기 위한 안정적인 네트워크 진입점
  • 기능: Pod 교체·IP 변경 시에도 클라이언트 접근 경로 유지
Client요청
→
Service고정 진입점
→
Pod A/B/C실제 처리
Client → Service → kube-proxy → Pod Network/CNI → Pod

경로① 상세 — Pod 생성

🎯 이 챕터를 끝내면: Control Plane이 결정하고, kubelet이 조정하고, CRI·CNI가 실행하는 구조 이해

  • 전체 순서: Control Plane이 실행 Worker Node 결정 → 선택된 Node의 kubelet이 생성·실행 관리 → 컨테이너 실행은 CRI, 네트워크 구성은 CNI에 위임
  • kubelet → CRI → CNI는 직렬 파이프라인이 아니라, kubelet이 Pod 실행을 조정하며 컨테이너 실행은 CRI에, 네트워크 구성은 CNI에 위임하는 구조

STEP 1구성요소 — kubelet · CRI · CNI

kubelet

Worker Node 관리자

각 Worker Node에서 실행, API Server가 할당한 Pod의 목표 상태(Desired State)를 실제 상태와 일치시키도록 지속 관리. 최초 실행뿐 아니라 상태 확인·재시작·볼륨 연결·보고까지 담당

CRI

Container Runtime Interface

프로그램이 아니라 kubelet과 Container Runtime 사이의 표준 인터페이스. kubelet이 Docker·containerd에 직접 종속되지 않도록 분리해 다양한 Runtime을 사용 가능하게 함

CNI

Container Network Interface

컨테이너 실행만으로는 미완료 — Pod가 고유 IP로 통신하려면 네트워크 구성이 필요. Pod Network → Pod CIDR → IPAM 순서로 이어지는 세 요소를 구성

STEP 2Pod Network → Pod CIDR → IPAM

예시 — 전체 Pod Network 10.244.0.0/16, Node 2개 기준
Worker Node 1                      Worker Node 2
Pod CIDR: 10.244.1.0/24            Pod CIDR: 10.244.2.0/24
 ├─ Pod A → 10.244.1.2              ├─ Pod D → 10.244.2.2
 ├─ Pod B → 10.244.1.3              └─ Pod E → 10.244.2.3
 └─ Pod C → 10.244.1.4

Pod Network

  • 정의: Pod들이 서로 통신하기 위해 사용하는 네트워크 영역
  • 기본 원칙: 각 Pod가 고유 IP를 보유
  • 범위: 같은 Node뿐 아니라 다른 Node의 Pod와도 통신 가능하도록 구성
  • 구현 주체: 실제 연결성은 Calico, Cilium, Flannel 등 CNI 구현체가 구성
Node 간 통신 예시
Worker Node 1                     Worker Node 2

Pod A                             Pod C
10.244.1.2  ───────────────────▶  10.244.2.2

Pod CIDR — Node별 대역 할당

  • 정의: CIDR(10.244.1.0/24 형식)로 표현되는 IP 주소 범위, Node별로 Pod가 사용할 IP 범위를 분할
  • 할당 주체: kube-controller-manager(Node IPAM Controller) — 전체 Pod Network(--cluster-cidr)를 Node 개수만큼 분할
  • 주의: Node별 /24 분할은 가장 일반적인 개념 설명용 구조이며, 실제 구현은 CNI마다 차이
Node별 대역 할당 과정
① 클러스터 생성 시 전체 Pod Network 지정 (--cluster-cidr=10.244.0.0/16)
② 신규 Node join 시 Node IPAM Controller가 분할된 CIDR 하나 배정
③ 해당 Node의 kubelet·CNI가 자신에게 할당된 podCIDR 확인
④ 이후 Pod 생성 시, CNI/IPAM은 이 podCIDR 범위 안에서만 개별 Pod IP 할당

IPAM & Pod Sandbox

  • IPAM(IP Address Management) — Pod CIDR 내 사용 가능한 IP를 찾아 Pod에 배정·관리하는 기능
  • 관리 대상: 사용 중/비어 있는 IP 목록, 신규 Pod IP 배정, Pod 삭제 후 IP 반환
  • Pod Sandbox — 컨테이너가 여러 개여도 Kubernetes에서 Pod는 하나의 네트워크 단위. 같은 Pod 내 컨테이너는 동일한 Network Namespace·Pod IP 공유
신규 Pod 생성 시 IPAM 동작
10.244.1.2 → Pod A 사용 중
10.244.1.3 → Pod B 사용 중
10.244.1.4 → 사용 가능  ─┐
10.244.1.5 → 사용 가능   ├─ IPAM이 검색 → 10.244.1.4 선택 → Pod C에 할당
                         ┘
💡 핵심 한 줄 요약CNI = 네트워크 전체 구성 담당, IPAM = 그중 IP 주소 할당만 담당. Kubernetes 네트워킹의 기본 단위는 컨테이너가 아니라 Pod

3

경로② 상세 — 트래픽 전달

🎯 이 챕터를 끝내면: Service는 고정된 진입점, 실제 배달은 각 Node의 kube-proxy가 담당한다는 구조 이해

  • 전체 순서: 클라이언트가 Service IP로 요청 → 요청 받은 Node의 kube-proxy가 실제 Pod로 전달(로드밸런싱)
  • Service는 고정된 논리적 진입점 역할만 하고, 트래픽을 실제 Pod로 보내는 실행은 각 Node의 kube-proxy가 담당

STEP 1구성요소

Service(ClusterIP)

고정 논리적 진입점

가상 IP(10.96.0.10:80)로 노출되는 고정 진입점, 실제 Pod가 아닌 논리적 주소. Selector로 매칭되는 Pod 목록(Endpoints)을 Endpoint Controller가 실시간 갱신

kube-proxy

Node별 규칙 엔진

각 Worker Node에서 실행, Service IP 트래픽을 실제 Pod IP로 로드밸런싱. iptables 또는 IPVS 규칙으로 동작하며 Endpoint 목록을 watch, Node마다 개별 실행

STEP 2전체 흐름 — 요청 처리 3단계

① Service 요청curl 10.96.0.10:80
→
② kube-proxy 전달로드밸런싱 → Pod B
→
③ 응답 반환Pod B → 클라이언트
  • 핵심: 클라이언트는 Service IP만 알면 되고, 실제 어떤 Pod가 응답했는지·Pod IP가 바뀌었는지는 알 필요 없음
구성요소핵심 역할
Service(ClusterIP)고정된 논리적 진입점, Endpoints(Pod 목록) 관리
kube-proxyService IP 트래픽을 실제 Pod로 로드밸런싱하는 Node별 규칙 엔진
Service = 고정된 논리적 진입점(Endpoints 관리), kube-proxy = Service IP 트래픽을 실제 Pod로 로드밸런싱하는 각 Node의 규칙 엔진

종합 — Service → Pod Packet Flow 추적

🎯 이 챕터를 끝내면: 경로①(Pod 생성)과 경로②(트래픽 전달)를 하나의 시나리오로 이어서 추적

예시 시나리오: 클라이언트가 nginx-service(ClusterIP 10.96.0.10:80)로 요청 → 실제로는 Worker Node 1의 Pod B(10.244.1.3)가 응답

0단계사전 조건 — 경로① 결과물

  1. Control Plane이 Worker Node 1을 선택 → kubelet이 nginx Pod 생성·실행 관리
  2. CRI를 통해 Container Runtime이 컨테이너 실행
  3. CNI가 Node 1의 Pod CIDR(10.244.1.0/24) 범위 안에서 IPAM으로 Pod IP 10.244.1.3 할당
  4. Endpoint Controller가 nginx-service의 Endpoints에 10.244.1.3(Pod B)을 등록

1~4단계요청 처리 (경로② 실행)

  1. 클라이언트가 Service로 요청 — curl 10.96.0.10:80 실행, 패킷의 목적지는 nginx-service의 ClusterIP·Port. 이 시점 클라이언트는 실제 Pod IP를 전혀 모름
  2. kube-proxy가 목적지 Pod 선택 — 요청이 도달한 Node(예: Node 1)의 kube-proxy가 Endpoints 목록(10.244.1.2, 10.244.1.3, 10.244.2.3 등)을 조회, 로드밸런싱(예: 라운드로빈)으로 10.244.1.3(Pod B) 선택
  3. 선택된 Pod로 패킷 전달 — kube-proxy가 iptables/IPVS 규칙에 따라 목적지를 10.96.0.10:80 → 10.244.1.3으로 실제 전달, 여기서부터는 경로①에서 CNI가 구성해 둔 Pod Network를 타고 이동
  4. Pod가 응답을 클라이언트에게 반환 — Pod B(10.244.1.3)가 요청 처리 후 응답 패킷 생성, 응답은 왔던 경로(kube-proxy)를 되짚어 클라이언트로 반환
단계주체핵심 동작
0(사전)kubelet·CRI·CNI·IPAMPod 생성 및 IP(10.244.1.3) 할당, Endpoints 등록
1클라이언트Service IP(10.96.0.10:80)로 요청
2kube-proxyEndpoints 조회 → 대상 Pod(10.244.1.3) 선택
3kube-proxy → Pod Network선택된 Pod로 패킷 전달
4Pod → 클라이언트응답 반환
경로①(kubelet·CRI·CNI·IPAM)이 통신 가능한 Pod를 미리 만들어두고, 경로②(Service·kube-proxy)가 요청이 올 때마다 그 Pod로 트래픽을 실제로 배달한다
