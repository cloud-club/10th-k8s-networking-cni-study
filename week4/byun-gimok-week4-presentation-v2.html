1. Flannel Architecture / VXLAN

Flannel이란?

서로 다른 노드에 있는 Pod 간 통신을 구현하려면 노드 간 네트워크 연결을 제공하는 구현체가 필요함. Kubernetes에서는 일반적으로 CNI 규격과 연동하는 네트워크 플러그인을 사용하며, Flannel은 대표적인 선택지 중 하나임.

Flannel은 Kubernetes에서 Pod 간 L3 네트워크를 간단하게 구성할 수 있도록 설계된 네트워크 솔루션임. Overlay 구성을 지원하며, 이번에 다루는 VXLAN 구성에서는 원래의 Ethernet 프레임을 VXLAN·UDP·IP 헤더로 한 번 더 감싸 서로 다른 노드 사이에 전달함. 목적지 노드에서는 바깥쪽 포장을 제거한 뒤 Pod에 전달함.

구성 요소와 역할

flanneld는 노드별 네트워크 정보를 관리하고, 선택한 백엔드에 따라 노드 간 연결을 준비함. 아래는 Linux + VXLAN + bridge 연결을 사용하는 예시임. Flannel의 DirectRouting은 비활성 상태로 가정함.

구성 요소역할레거시 대응 — 학습용 비유
flanneld노드별 서브넷·네트워크 정보 관리서버별 가상 네트워크 관리 에이전트에 가까움
bridge / vethPod와 노드 내부 네트워크 연결가상 NIC와 vSwitch 연결에 가까움
VXLAN 장치노드 사이의 캡슐화·역캡슐화 처리데이터센터 VXLAN VTEP 역할과 유사함

VXLAN: 원래 패킷을 노드 간 전달용 패킷 안에 넣는 방식

안쪽에는 Pod 간 통신 정보가 유지되고, 바깥쪽에는 터널 양 끝의 Node IP가 사용됨. 목적지 노드에서 바깥 포장을 제거한 뒤 Pod에 전달함. 캡슐화 자체는 암호화를 의미하지 않음.

2. Calico Architecture / Routing / BGP

Calico는 Pod 연결과 네트워크 정책을 제공함. 여기서는 Linux의 일반적인 라우팅 기반 데이터 경로를 기준으로, CNI·IPAM·Felix·BGP의 책임을 구분함.

구성 요소담당 역할레거시 대응 — 학습용 비유
CNI / IPAMPod 연결 준비 / 사용할 IP 할당NIC 설정 프로그램 / IP 주소 관리 시스템
Felix노드의 경로와 정책 등의 설정 관리라우팅·분산 방화벽 설정 에이전트
BGP 구성 요소BGP를 사용하는 구성에서 경로 교환기존 라우터의 BGP 프로세스
Linux 데이터 경로구성된 경로와 정책으로 실제 패킷 처리라우터의 전달부와 방화벽 필터 처리부

BGP는 경로를 교환하는 프로토콜이며 VXLAN은 캡슐화 방식임. 둘은 같은 분류의 기술이 아님. Calico도 VXLAN·IPIP를 사용할 수 있으므로 “Calico = 항상 비캡슐화”로 고정할 수 없음.

공식 근거: Calico 구성 요소 · 네트워크 모드

3. Overlay vs Underlay

Underlay는 노드 사이의 실제 연결을 제공하는 기반 네트워크임. Overlay는 그 기반 위에 터널 등으로 구성한 논리 네트워크임. Overlay를 사용해도 Underlay는 여전히 필요함.

비교 기준Overlay 예시비캡슐화 라우팅 예시
노드 사이 패킷Pod 패킷을 터널 패킷으로 감싸 전달함추가 터널 없이 Pod IP를 목적지로 전달함
기반망 요구터널 양 끝인 Node IP에 도달 가능해야 함전달에 참여하는 L3 장비에 Pod 목적지 경로가 필요함
레거시 비교데이터센터 VXLAN 논리 네트워크에 가까움기존 서버 서브넷의 L3 라우팅에 가까움
구분할 점물리망을 없애는 기술이나 암호화 보장은 아님반드시 외부 라우터와 BGP를 연결해야 하는 것은 아님

같은 L2망의 노드끼리 직접 전달하는 비캡슐화 구성과, ToR 라우터까지 Pod 경로를 교환하는 구성은 구분해야 함. Flannel host-gw는 노드 간 직접 L2 연결을 요구함.

공식 근거: Calico 모드 비교 · Flannel host-gw

4. Pod-to-Pod Packet Flow 비교

공통 가정: Linux, 일반 Pod, IPv4, 서로 다른 두 노드, 정책상 통신 허용, 경로 정상 상태임. Pod IP 직접 통신만 비교하며 Service·kube-proxy·외부 NAT는 제외함. 모든 주소와 경로는 학습용 예시이며 실제 실습 결과가 아님.

대상Node IPPod IP
노드 A / Pod A192.168.10.1110.244.1.10
노드 B / Pod B192.168.10.1210.244.2.20
비교Flannel VXLAN 예시Calico 비캡슐화 예시
목적지 선택원격 Pod 대역을 원격 노드의 터널로 연결함학습한 경로로 원격 노드를 next hop으로 선택함
노드 사이 IP 헤더바깥 Node IP + 안쪽 Pod IP가 존재함터널 헤더 없이 원래 Pod IP로 전달함
기존 인프라 관점터널 종단에서 감싸기·풀기를 수행함일반적인 라우팅 테이블과 next hop으로 전달함

같은 노드의 Pod끼리라면 위 노드 간 터널 구간은 필요하지 않음. Flannel의 bridge 조합은 로컬 bridge를, 일반적인 Calico 구성은 호스트 라우팅을 중심으로 이해 가능함.

공식 근거: VXLAN · bridge 연결 · Calico 연결·라우팅

5. NetworkPolicy / IPAM

IPAM은 사용할 주소를 관리하고, NetworkPolicy는 어떤 통신을 허용할지 정의함. 주소가 배정되어 있어도 경로나 정책이 맞지 않으면 통신은 실패할 수 있음.

기능담당 영역레거시 대응 — 학습용 비유
IPAM주소 풀·할당·반환·사용 상태 관리Infoblox IPAM 같은 IP 주소 관리 기능
라우팅목적지로 가는 경로와 next hop 선택L3 라우터의 경로 테이블
NetworkPolicyPod에 대한 ingress / egress 허용 조건서버 그룹별 분산 방화벽·보안 그룹 정책

NetworkPolicy의 적용 범위

기본 Kubernetes NetworkPolicy는 Pod·Namespace 선택 조건, IP 대역, 포트 등을 이용함. 특정 방향의 격리 정책에 선택되지 않은 Pod는 해당 방향에서 기본적으로 비격리 상태임. 격리된 방향은 적용되는 정책의 허용 규칙을 합산함.

Pod A → Pod B 통신에서 출발지의 egress와 목적지의 ingress가 모두 격리되어 있다면 양쪽 조건을 모두 만족해야 함. 전통적 방화벽의 위에서 아래로 첫 일치 규칙을 적용하는 방식과 동일하지 않음. 여기서는 Calico 확장 정책의 별도 동작은 다루지 않음.

비교Flannel 예시Calico 예시
IPAMbridge + host-local 조합에서는 노드에 설정된 범위 안에서 주소를 할당함Calico IPAM은 IPPool의 주소 블록을 노드에 할당해 Pod IP를 관리함
정책 집행flanneld 자체가 아닌 별도 정책 컨트롤러·구현이 필요함Calico 정책 엔진으로 Kubernetes NetworkPolicy를 집행함

NetworkPolicy 객체만 생성하고 집행 가능한 네트워크 구현이 없다면 차단 효과가 발생하지 않음. 현재 Flannel 문서에는 별도 정책 컨트롤러를 함께 배포하는 선택지도 있으므로 “Flannel 구성에서는 정책을 절대 사용할 수 없음”으로 해석하면 안 됨.
