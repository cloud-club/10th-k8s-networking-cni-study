① CNI의 역할과 구조

네트워크 연결을 요청하는 공통 규약

CNI(Container Network Interface)는 컨테이너 런타임이 네트워크 플러그인에 연결 구성을 요청할 때 사용하는 표준 인터페이스임. 호출 방법과 설정·결과의 형식을 정하며, 실제 네트워크 구성은 플러그인이 수행함.

기존 가상화 환경에서는 VM에 가상 NIC를 연결하고 IP와 경로를 설정함. Pod도 네트워크 연결 구성이 필요하지만, CNI 자체가 가상 스위치인 것은 아님. CNI는 작업을 요청하는 규약이고, 플러그인은 해당 요청을 받아 설정하는 프로그램임.

구분역할
CNI 규약런타임과 플러그인 사이의 호출 방법 및 JSON 입출력 형식 정의
CNI 플러그인호출된 요청에 따라 네트워크 연결·해제와 관련 설정 수행
대표 명령ADD: 연결 구성 요청 / DEL: 연결 해제 요청

CNI가 표준화하는 것은 요청과 응답의 경계임. 노드 사이에서 패킷을 전달하는 구체적인 방법까지 하나로 정하는 것은 아님.

② CNI Plugin / IPAM

연결 구성과 주소 관리의 구분

네트워크 연결을 만드는 작업과 사용할 IP를 결정하는 작업은 구분됨. CNI 플러그인은 인터페이스 연결과 주소·경로 설정을 수행하며, IPAM(IP Address Management)은 주소의 할당과 반환, 할당 상태 관리를 담당함.

기존 인프라 기준으로 IPAM은 자동화된 IP 주소 대장에 가까움. 사용 가능한 주소를 배정하고 사용 상태를 기록하는 역할이며, 반드시 DHCP 방식으로 동작하는 것은 아님.

구분담당 작업예시
네트워크 연결 플러그인인터페이스 연결 및 IP·경로 적용bridge
IPAM 플러그인주소 할당·반환 및 할당 상태 관리host-local

bridge와 host-local의 역할 관계

  1. 런타임이 bridge 플러그인에 네트워크 연결을 요청함.
  2. bridge는 설정된 host-local IPAM에 사용할 주소를 요청함.
  3. host-local은 주소를 할당하고 결과를 반환함.
  4. bridge는 반환된 주소 정보를 인터페이스 설정에 사용함.

위 과정은 두 플러그인을 조합하는 예시임. 모든 CNI 구현체가 host-local을 사용하는 것은 아님. host-local은 노드 로컬에서 상태를 관리하므로, 노드 사이의 주소 범위가 겹치지 않도록 별도 관리가 필요함.

IPAM이 필요한 이유는 Pod 생성·삭제에 따라 달라지는 주소 사용 상태를 관리하기 위함. 주소 할당 성공만으로 통신 경로까지 완성되었다고 볼 수는 없음.

③ Primary CNI Overview

Pod의 기본 네트워크를 구성하는 구현체

이 정리에서 Primary CNI는 Pod의 기본 네트워크를 담당하는 구현체를 의미함. 대표적으로 Flannel, Calico, Cilium을 비교함.

일반적으로 “CNI 설치”는 CNI 실행 파일만 배치하는 것이 아니라, 네트워크 상태를 관리하는 에이전트 등을 포함한 솔루션을 설치한다는 의미로 사용됨.

구분담당 역할
CNI 실행 파일런타임의 요청을 받아 Pod 네트워크 연결·해제 작업 수행
상주 에이전트노드와 정책 등의 변화에 맞춰 네트워크 상태 갱신
데이터 경로설정된 커널 경로·규칙 등을 통해 실제 패킷 처리

네트워크를 설정하는 작업과 설정된 네트워크로 패킷이 이동하는 과정은 별개임. 패킷이 이동할 때마다 CNI 실행 파일을 호출하는 구조는 아님.

상주 에이전트서버별 네트워크 관리 에이전트설정·정책 변화를 각 노드의 네트워크 상태에 반영하는 담당임. Calico의 Felix와 Cilium의 cilium-agent가 예시임.

④ Flannel / Calico / Cilium Overview

기본 구성과 특징 비교

세 구현체는 Pod 네트워크 연결을 제공한다는 공통점이 있지만, 기본 구성과 함께 제공하는 기능에 차이가 있음.

구분기본 구성·특징NetworkPolicy
Flannelflanneld가 노드별 네트워크 정보를 관리하며, VXLAN·host-gw 등의 방식으로 노드 간 Pod 연결 제공Flannel 단독으로는 별도 정책 구현 필요
CalicoCNI·IPAM·Felix 등으로 연결과 정책을 구성하며, IP-in-IP·비캡슐화·VXLAN 등의 전달 방식을 선택 가능함지원
Ciliumcilium-agent가 eBPF 기반 네트워크·보안 기능을 관리하며, Hubble을 통한 관측 기능 제공지원

Flannel은 기본 Pod 연결, Calico는 네트워킹과 정책, Cilium은 eBPF 기반 네트워킹·보안·관측을 중심으로 특징을 구분할 수 있음. 이는 학습을 위한 비교 기준이며, 제품별 기능 전체를 한 가지 역할로 제한하는 의미는 아님.

제품 이름만으로 실제 패킷 경로를 고정해서 판단할 수는 없음. 같은 구현체도 설정에 따라 터널 사용 여부와 라우팅 방식이 달라질 수 있음.

참고: Flannel · Calico architecture · Cilium introduction

Calico의 기본 구성과 역할

Calico는 Pod 네트워크 연결과 통신 정책을 제공하는 구현체임. 아래 구성도에서는 연결 준비·주소 관리·노드 설정·경로 교환의 역할 구분을 중심으로 확인함. 모든 구성 요소가 모든 설치에서 동일하게 사용되는 것은 아님.

핵심 구성역할레거시 기능과의 비교
CNI 플러그인Pod의 네트워크 연결 준비를 담당함NIC 연결·설정을 수행하는 자동화 프로그램에 가까움
IPAMPod에 사용할 IP를 할당·관리함IP 주소 관리 시스템에 가까움
Felix노드의 로컬 경로·인터페이스·정책 등을 설정함서버별 네트워크·분산 방화벽 설정 에이전트에 가까움
BGP 구성 요소사용하는 구성에서 노드 간 경로를 교환함기존 라우터의 경로 교환 기능에 가까움

Calico는 IP-in-IP·비캡슐화·VXLAN 등의 전달 방식을 선택할 수 있음. 이번 주에는 하나의 고정된 전달 방식만 제공하는 제품은 아님을 구분하는 수준으로 정리함.

Flannel가상 네트워크 연결 솔루션 / NSX의 연결 기능 일부가상 스위치 연결과 노드 간 터널 또는 라우팅 구성을 묶어 이해하기 적절함. 기본 Pod 연결이 중심이며, Flannel 자체가 NetworkPolicy까지 집행하는 것은 아님.
