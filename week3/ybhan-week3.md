# W3. CNI Overview &amp; Cloud Native Networking Landscape

## 1. W2에서 이어지는 질문

W2에서는 kubelet → CRI → 런타임 → CNI 순서로 Pod가 네트워크를 받는 흐름을 확인했습니다. 그때 CNI는 '연결을 만들어주는 무언가' 정도로만 생각되었습니다. W3에서는 **CNI가 규격으로서 정확히 무엇을 정해두었는지**, 그리고 **그 규격을 지키는 구현체들이 왜 이렇게 여러 개인지**를 알아보려 합니다.

[[Core Kubernetes]] 5장을 아주 많이 참고했습니다.



## 2. SDN으로서의 Kubernetes 네트워크

Kubernetes 네트워크는 소프트웨어로 정의(SDN)됩니다. Pod와 Service 엔드포인트가 계속 생기고 사라지기 때문에 고정된 배선으로는 감당이 안 되고, 상태가 바뀔 때마다 규칙을 다시 써주는 도구가 필요합니다.


| 약어   | 원어                          | W3 주제 관점에서의 의미           |
| ---- | --------------------------- | ------------------------ |
| SDN  | Software-Defined Networking | 네트워크 구성을 소프트웨어가 계속 갱신    |
| CNI  | Container Network Interface | 런타임과 네트워크 플러그인 사이의 호출 규격 |
| IPAM | IP Address Management       | 주소를 주고 회수하는 책임           |
| BGP  | Border Gateway Protocol     | 인터넷에서 쓰는 L3 경로 광고 프로토콜   |
| OVS  | Open vSwitch                | 커널 기반의 프로그래머블 가상 스위치     |
| XDP  | eXpress Data Path           | NIC 드라이버 지점에서 패킷을 처리하는 훅 |


여기서 풀어야 할 문제는 하나입니다. **한 클러스터에 수천 개의 컨테이너가 있어도 각자 라우팅 가능한 고유 IP를 갖게 하는 것.** CNI는 이걸 모듈식으로 나눠서 해결합니다.



## 3. CNI가 표준으로 제공하는 것

### 3.1 규격 내

CNI 명세가 정의하는 건 컨테이너 런타임이 지금 시작 중인 프로세스의 네트워크를 요청하는 계약이라는 것뿐입니다.


| 구성 요소 | 내용                                           |
| ----- | -------------------------------------------- |
| 오퍼레이션 | `ADD` / `DEL` / `CHECK` (+ 버전 확인용 `VERSION`) |
| 입력    | netns 경로, 컨테이너 ID, 인터페이스 이름, JSON 설정         |
| 출력    | 만들어진 인터페이스, 할당된 IP, 경로, DNS 정보               |
| 실행 방식 | 바이너리 실행 파일 호출                                |


`ADD`와 `DEL`은 containerd가 Pod를 시작하거나 지울 때 호출됩니다. W2에서 확인한 대로 CNI는 Pod 생성 시점에 한 번 실행되고 끝나고, 그 뒤로는 만들어둔 인터페이스와 경로를 커널이 사용하는 구조입니다.

참고자료: [CNI SPEC](https://github.com/containernetworking/cni/blob/main/SPEC.md)

### 3.2 규격 외

명세가 좁게 잡혀 있으니 과연 표준이라고 부를 만한 게 무엇인지 궁금해서 정리해봤는데, CNI가 표준인 범위는 호출 방식과 주고받는 값의 모양까지가 아닐까 싶습니다.


| 표준           | 비표준 (구현체 자유)                 |
| ------------ | ---------------------------- |
| 언제 호출되는지     | 노드 사이를 어떻게 잇는지 (라우팅/터널/eBPF) |
| 무엇을 넘겨받는지    | NetworkPolicy를 구현할지, 어떻게 할지  |
| 무엇을 돌려주는지    | 관측, 모니터링 통합                  |
| 실패를 어떻게 알리는지 | 암호화, kube-proxy 대체 여부        |


CNI를 바꿔 끼워도 Pod가 뜨는 흐름은 그대로인데, **패킷이 노드를 넘어가는 방식**은 완전히 달라집니다. 표준이 얇게 잡혀 있는 덕분에 공급자도 여러 개가 존재할 수 있습니다.

### 3.3 설정 파일과 바이너리

노드에는 설정 파일과 바이너리 둘 다 있어야 합니다. 둘 중 하나만 있으면 Pod의 네트워크 준비가 실패하고, W2에서 본 대로 sandbox 단계에서 막힙니다.

```text
/etc/cni/net.d/     → 어떤 플러그인을 어떤 설정으로 쓸지 적은 JSON
/opt/cni/bin/       → 실제로 실행될 플러그인 바이너리
```



## 4. IPAM은 왜 따로 있을까

CNI 설정은 보통 **연결을 만드는 플러그인**과 **주소를 주는 IPAM 플러그인**을 따로 적습니다. 


| 구분   | 담당                   | 예시                                    |
| ---- | -------------------- | ------------------------------------- |
| main | 인터페이스를 만들고 netns에 연결 | ptp, bridge, macvlan                  |
| ipam | 주소를 골라주고 회수          | host-local, calico-ipam, dhcp, static |
| meta | 부가 기능을 얹음            | portmap, bandwidth, tuning            |


나눠둔 이유는 **연결 방식은 그대로 두고 주소 관리 방식만 바꿀 수 있게** 하기 위해서입니다. 노드 로컬 파일로 관리하다가(host-local) 클러스터 전체에서 관리하는 방식(calico-ipam)으로 옮겨도 인터페이스를 만드는 코드는 안 건드려도 됩니다.

IPAM이 없으면 주소가 겹칩니다. 겹치면 경로가 잘못 잡히고, 어느 Pod로 갈지 알 수 없게 됩니다. 반대로 IPAM이 기록해둔 상태와 실제 쓰는 상태가 어긋나면 주소가 남아서 새 Pod에 줄 주소가 모자라집니다(주소 누수).

노드마다 podCIDR을 쪼개주는 방식이면 경로를 노드 단위로 한 줄만 적으면 되지만, 노드마다 안 쓰는 주소가 남습니다. W2에서 정리한 Pod CIDR 트레이드오프가 여기서 그대로 반복됩니다.



## 5. Primary CNI의 공통 아키텍처

Calico와 Antrea 모두 **데몬셋 + 조정 컨테이너** 구조입니다. 다른 Primary CNI들도 대체로 이 모양을 따릅니다.

```text
노드마다 (DaemonSet)
├─ 에이전트 파드: 커널 경로/규칙을 실제로 씀, hostPath로 노드 파일시스템 마운트
└─ initContainer: /opt/cni/bin, /etc/cni/net.d 에 바이너리와 설정을 복사

클러스터 전체 (Deployment)
└─ 조정 컨트롤러: API Server를 보고 노드, Pod, 정책 메타데이터를 집계
```

책에서 정리한 설치 4단계:

1. **kube-proxy 설치**: 조정 컨트롤러가 API Server를 쿼리해야 할 수 있어서 선행하며 보통 클러스터 설치 때 이미 끝나 있음
2. **노드에 CNI 바이너리 설치:** 런타임이 호출할 수 있는 자리에 둠
3. **데몬셋 배포**: 노드별 에이전트
4. **조정 컨테이너 배포**: 메타데이터 집계, 프록시 처리

에이전트가 `hostPath`를 마운트하는 이유는, 컨테이너 안에서 노드의 커널 설정과 CNI 디렉터리를 건드려야 하기 때문입니다. CNI는 파드로 배포되지만 실제 작업 대상은 노드라는 점이 헷갈리기 쉬운 부분.



## 6. 데이터 플레인을 가르는 축

CNI를 비교하려니 노드를 넘는 패킷을 어떻게 처리하는지 보게 됩니다.


| 축        | 방식                   | 대표                     |
| -------- | -------------------- | ---------------------- |
| L2 브리지   | 노드 로컬 가상 스위치에 포트를 꽂음 | OVS(Antrea), bridge    |
| L3 라우팅   | Pod 경로를 경로 테이블로 광고   | BGP(Calico)            |
| 오버레이/터널  | 패킷을 감싸서 보냄           | VXLAN(Flannel), IPIP   |
| eBPF/XDP | 커널 훅에서 직접 처리         | Cilium, Calico eBPF 모드 |


다만 이 차이를 최종 사용자는 거의 못 느낍니다.

관리자 쪽에서 '기존 라우터와 BGP로 피어링하고 싶다'거나 'OVS 기반으로 트래픽을 들여다보고 싶다'는 니즈가 있으면 따져봄직합니다.



## 7. Primary CNI Overview


| CNI                                | kube-proxy 대체   | 메모                            |
| ---------------------------------- | --------------- | ----------------------------- |
| KindNet                            | X               | kind 기본값, 단일 서브넷 전제의 최소 구현    |
| Flannel                            | X               | 한때 운영 클러스터의 주력, 지금은 사용 감소     |
| Calico                             | O (eBPF 모드)     | 노드별 IP 풀을 쪼개고 커널 경로 테이블과 맞춤   |
| Antrea                             | O (AntreaProxy) | Calico와 유사한 고급 옵션, OVS 기반 관측  |
| Cilium                             | O               | 커널 트래픽 관리 없이 최신 Linux API로 처리 |
| 클라우드 계열 (GKE, EC2/VPC, NCP, Azure) | 벤더별             | 노드 경로를 거치지 않는 직접 라우팅, 이식성은 낮음 |


Calico나 Antrea처럼 벤더 특화 기능(Tigera, NSX 통합 등)과 중립 기능을 둘 다 제공하는 경우도 있습니다.

### 대표 CNI 한 줄 정리

- **Flannel**: 주소를 나눠주고 노드끼리 터널로 이어줌. 단순한 만큼 정책은 없음.
- **Calico**: 경로를 L3로 광고해서 오버레이 없이 붙임. 정책과 kube-proxy 대체까지 확장.
- **Cilium**: 패킷 처리 자체를 eBPF로 내림. IP가 아니라 워크로드 Identity로 정책을 판단.



## 8. kube-proxy와 CNI의 관계

kube-proxy는 사용자가 SDN에서 가장 먼저 만나는 요소지만, **역할은 Service IP를 Pod IP로 매핑하는 것 하나**입니다. 그래서 Pod 네트워크가 제대로 없으면 kube-proxy만으로는 아무것도 안 됩니다. 매핑할 대상이 없기 때문.


|     | kube-proxy               | CNI           |
| --- | ------------------------ | ------------- |
| 대상  | Service → Pod 매핑         | Pod의 연결과 주소   |
| 계기  | Service/EndpointSlice 변경 | Pod 생성, 삭제    |
| 산출물 | 노드의 전달 규칙                | 인터페이스, 주소, 경로 |


**왜 대체하려 하는가**: kube-proxy에서 Kubernetes에 가장 중요하게 쓰이는 iptables 기능은 NAT. 그런데 Service와 Pod는 계속 바뀌고, 규칙은 위에서부터 순서대로 평가되기 때문에 규모가 커지면 규칙 수와 갱신 비용이 같이 커집니다. Calico의 eBPF 모드나 Cilium, AntreaProxy는 이 부분을 자기 데이터 플레인 안으로 끌어와서 처리합니다.

**그런데 왜 설치는 선행되는가**: 설치 순서와 최종 상태는 다른 얘기입니다. CNI의 조정 컨트롤러가 뜨려면 API Server에 닿아야 하는데, 그 접근 자체가 ClusterIP를 거칩니다. 즉 **CNI가 올라오기 전까지는 kube-proxy가 부트스트랩을 담당**하고, 대체 모드를 켠 뒤에 걷어내는 순서가 됩니다.
