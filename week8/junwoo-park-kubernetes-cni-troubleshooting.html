패킷이 지나가는 경로

Pod A에서 curl http://web 을 실행했을 때 거치는 구간입니다. 테두리 색이 담당 영역을 나타냅니다.

트러블슈팅 전에 알아야 할 사실

현장에서 원인 파악이 늦어지는 경우는 대부분 아래 내용을 놓쳤을 때입니다.

ClusterIP는 ping이 되지 않는 경우가 많습니다

ClusterIP는 실제 인터페이스에 붙은 주소가 아니라 변환 규칙에만 존재하는 가상 IP입니다. 확인할 때는 ping 대신 서비스 포트로 curl을 실행해야 합니다.

Pod가 Running이어도 네트워크가 정상이라는 뜻은 아닙니다

Running은 컨테이너가 실행 중이라는 의미입니다. 정책, 라우트, DNS는 별도로 확인해야 합니다.

NetworkPolicy는 CNI가 지원해야 적용됩니다

Flannel만 설치한 클러스터에서는 NetworkPolicy를 만들어도 트래픽이 차단되지 않습니다. Calico와 Cilium은 정책을 직접 적용합니다.

Service 장애의 원인은 kube-proxy보다 Endpoints인 경우가 많습니다

selector 불일치나 readiness 실패로 EndpointSlice가 비어 있으면 kube-proxy가 정상이어도 연결되지 않습니다.

노드 간 통신은 클러스터 밖의 설정에도 영향을 받습니다

방화벽, 보안 그룹, 클라우드 라우트 테이블이 터널 포트나 BGP를 막으면 CNI 설정이 정상이어도 통신되지 않습니다.

CNI 에이전트는 노드마다 하나씩 실행됩니다

일부 노드에서만 문제가 생기면, 클러스터 전체가 아니라 그 노드의 에이전트 상태와 로그를 먼저 확인해야 합니다.

오류 메시지로 원인 범위 좁히기

같은 통신 실패라도 오류 메시지에 따라 확인할 곳이 달라집니다.

오류의미먼저 확인할 곳

설치 namespace는 설치 방법에 따라 다릅니다. Flannel은 kube-flannel(이전 매니페스트는 kube-system), Calico는 calico-system(매니페스트 설치는 kube-system), Cilium은 보통 kube-system에 설치됩니다. 그래서 -A 옵션으로 먼저 찾습니다. CNI 에이전트는 노드마다 하나씩 있으므로 문제가 있는 노드의 Pod 로그를 확인합니다.
공통으로 먼저 실행하는 명령

$ kubectl get nodes -o wide
$ kubectl get pods -A -o wide \
    | grep -E 'flannel|calico|cilium|kube-proxy|coredns'

# 2. 비정상 Pod와 이벤트
$ kubectl get pods -A -o wide | grep -v Running
$ kubectl describe pod <pod> | sed -n '/Events/,$p'

# 3. 문제 노드의 CNI Pod를 찾아 로그 확인
$ kubectl get pods -A -o wide --field-selector \
    spec.nodeName=<node> | grep -E 'flannel|calico|cilium'
$ kubectl -n <namespace> logs <cni-pod> --tail=50

# 4. 디버그 Pod에서 통신 확인
$ kubectl run netshoot --image=nicolaka/netshoot \
    -it --rm -- bash

# 5. 노드에서 패킷 확인
$ sudo tcpdump -ni any host <ip> -c 20

결과 해석

같은 노드의 Pod는 성공하고 다른 노드의 Pod에서 처음 실패했으므로, 원인은 노드 간 경로에 있습니다. Pod 네트워크 생성과 같은 노드 통신은 확인할 필요가 없습니다.

양쪽 노드에서 캡처하는 이유

보내는 노드에는 패킷이 보이는데 받는 노드에 없다면, 두 노드 사이의 방화벽, 보안 그룹, 스위치를 확인해야 합니다.

두 노드에서 모두 패킷이 보이는데도 통신되지 않는다면, 수신 노드에서 캡슐을 풀어 Pod로 전달하는 CNI 쪽을 확인해야 합니다.

통신 단계는 모든 CNI에서 같습니다. 그 단계를 구현하는 컴포넌트와 확인 명령이 CNI마다 다릅니다.

Flannel가장 단순한 오버레이 CNI

구조가 단순해서 통신 단계와 컴포넌트가 거의 1대1로 대응합니다. 대신 NetworkPolicy는 지원하지 않습니다.

컴포넌트와 담당 영역

  • kube-controller-manager가 노드마다 podCIDR를 할당합니다.
  • flanneld가 서브넷 정보를 subnet.env 에 기록하고, VXLAN 장치 flannel.1 과 FDB를 관리합니다.
  • CNI 플러그인(bridge, host-local)이 veth를 cni0 에 연결하고 IP를 할당합니다.

이 증상이면 이 컴포넌트를 확인합니다

  • flanneld가 반복 재시작합니다. 노드의 .spec.podCIDR 가 비어 있는지 확인합니다.
  • Pod 생성에 실패합니다. host-local 할당 파일과 서브넷 고갈 여부를 확인합니다.
  • 다른 노드로만 통신되지 않습니다. flannel.1, fdb, UDP 8472를 확인합니다.
  • 정책이 적용되지 않습니다. Flannel에는 정책 엔진이 없습니다.

$ cat /run/flannel/subnet.env
FLANNEL_NETWORK=10.244.0.0/16

Calico라우팅과 NetworkPolicy 중심 CNI

컴포넌트 역할이 나뉘어 있어서 라우트 문제와 정책 문제를 구분해서 확인할 수 있습니다.

컴포넌트와 담당 영역

  • calico-ipam이 IPPool을 노드별 /26 블록으로 나눠 할당합니다.
  • Felix가 노드의 라우트와 정책(iptables 또는 eBPF)을 설정합니다.
  • BIRD가 BGP로 Pod 블록 라우트를 다른 노드와 교환합니다.
  • kube-controllers, Typha가 리소스를 동기화하고 대규모 클러스터에서 부하를 분산합니다.

이 증상이면 이 컴포넌트를 확인합니다

  • Pod 생성에 실패합니다. IPPool과 블록 사용량을 확인합니다.
  • 다른 노드로만 통신되지 않습니다. BGP peer 상태와 IPIP(IP 프로토콜 4) 허용 여부를 확인합니다.
  • 특정 통신만 차단됩니다. 정책, cali-* 체인, Felix 로그를 확인합니다.

CiliumeBPF 기반 CNI

iptables 규칙 대신 eBPF 맵을 확인합니다. Hubble로 드롭된 사유를 직접 볼 수 있습니다.

컴포넌트와 담당 영역

  • cilium-agent가 eBPF 프로그램을 로드하고 endpoint, identity, Service 맵을 관리합니다.
  • cilium-operator가 IPAM(CiliumNode)을 할당하고 CRD를 정리합니다.
  • 터널 또는 native 라우팅이 노드 간 전달 방식을 결정합니다.
  • Hubble이 플로우별 verdict와 드롭 사유를 보여줍니다.

이 증상이면 이 컴포넌트를 확인합니다

  • 정책 때문에 차단됩니다. hubble observe --verdict DROPPED 를 실행합니다.
  • Service 접속이 안 됩니다. cilium-dbg service list 와 kube-proxy 공존 여부를 확인합니다.
  • 다른 노드로만 통신되지 않습니다. Cluster health와 터널 포트를 확인합니다.
  • endpoint가 비정상입니다. agent 로그와 endpoint list 를 확인합니다.

사례 5-1. 정책 차단: 동작 규칙과 흔한 실수

증상: 같은 Service인데 특정 Pod에서만 timeout이 발생합니다. 최근에 NetworkPolicy를 추가했거나 라벨을 변경했습니다.

정책이 동작하는 규칙

  • Pod를 선택하는 정책이 하나라도 있으면, 그 방향(Ingress 또는 Egress)은 허용 목록에 있는 트래픽만 통과합니다.
  • 정책은 허용만 더하며, 여러 정책은 합쳐서 적용됩니다.
  • 클라이언트의 egress와 서버의 ingress에 정책이 모두 있으면 양쪽에서 허용해야 합니다.
  • Service로 접근해도 정책은 변환된 Pod IP를 기준으로 적용됩니다.
  • DNS(53)도 egress 정책의 대상입니다.
timeout과 refused
대부분의 정책 엔진은 차단한 패킷을 버리므로 timeout으로 보입니다. 다만 방화벽의 REJECT 규칙은 refused로 보일 수 있습니다. 목적지에서 SYN이 도착하는지 캡처로 확인해야 정확히 구분됩니다.
흔한 실수: selector를 한 항목에 쓸지, 두 항목으로 나눌지
# 의도: shop 네임스페이스의 app=web Pod만 db 접근 허용

# 잘못된 작성: 항목이 둘이므로 OR로 동작합니다.
ingress:
- from:
  - namespaceSelector:
      matchLabels: {kubernetes.io/metadata.name: shop}
  - podSelector:
      matchLabels: {app: web}
# shop의 모든 Pod, 그리고 정책과 같은 네임스페이스의 app=web Pod가
# 모두 허용됩니다.

# 올바른 작성: 한 항목 안에 두 selector를 쓰면 AND입니다.
ingress:
- from:
  - namespaceSelector:
      matchLabels: {kubernetes.io/metadata.name: shop}
    podSelector:
      matchLabels: {app: web}

사례 5-2. 정책 차단: CNI별 확인과 조치

정책을 확인하는 방법과 드롭 사유를 보는 방법이 CNI마다 다릅니다.

CNI정책 확인 방법
Flannel정책을 적용하지 않습니다. 정책이 있어도 차단되지 않으므로, 통신이 막힌다면 다른 원인입니다. 정책이 필요하면 Calico 또는 Cilium을 사용합니다.
CalicoKubernetes 정책은 knp.<ns>. 이름으로 보입니다. 정책에 Log 규칙을 넣고 커널 로그의 calico-packet 를 확인합니다.
Ciliumendpoint의 정책 적용 여부를 보고, Hubble 또는 monitor로 드롭 사유를 확인합니다. 감사 모드로 먼저 영향을 확인할 수 있습니다.

조치

  • 차단된 출발지의 라벨과 네임스페이스를 확인해 허용 규칙에 추가합니다.
  • selector 작성 방식(AND와 OR)을 점검합니다.
  • egress 정책에는 DNS 허용을 함께 넣습니다.
  • 운영에 적용하기 전에 로그나 Hubble로 영향 범위를 확인합니다.

사례 6-1. 외부 통신 실패: 출발지 주소 변화와 원인

증상: Pod에서 클러스터 밖으로 접속하면 응답이 없습니다. 패킷의 출발지 주소가 지점마다 어떻게 바뀌는지 알아야 원인을 찾을 수 있습니다.

원인 후보나타나는 증거확인 방법
SNAT 규칙 없음노드 eth0 캡처에서 출발지가 Pod IP입니다.노드의 iptables nat, CNI 설정
ip_forward 또는 rp_filter노드가 Pod의 패킷을 전달하지 않습니다.sysctl 값 확인
노드의 기본 라우트노드 자신도 외부에 접속하지 못합니다.ip route get 1.1.1.1
클라우드 NAT, 라우트, 보안 그룹SNAT은 됐는데 응답이 없습니다.노드에서 직접 curl과 비교
외부 방화벽 허용 목록일부 노드에서만 성공합니다.노드별 출구 공인 IP 확인
MTU, PMTUD작은 요청은 되고 큰 응답에서 멈춥니다.ping -M do -s

사례 6-2. 외부 통신 실패: 확인과 조치

노드 자체의 외부 통신부터 확인한 뒤, 패킷의 출발지 주소와 SNAT 규칙을 확인합니다.

확인 순서

  • 노드에서 직접 외부에 접속해 노드 자체가 정상인지 확인합니다.
  • Pod에서 외부 IP로 접속해 DNS와 구분합니다.
  • 노드 eth0에서 캡처해 출발지 주소를 확인합니다.
  • SNAT 규칙과 ip_forward 를 확인합니다.
  • SNAT이 되는데도 실패하면 클라우드 설정을 확인합니다.

CNI별 SNAT 설정

  • Flannel --ip-masq 옵션
  • Calico IPPool의 natOutgoing: true
  • Cilium enable-ipv4-masquerade 설정
외부 방화벽이 출구 IP를 허용 목록으로 관리한다면, 노드 IP가 아니라 고정된 출구 IP가 필요합니다. 이때는 Egress Gateway 기능을 검토합니다.
노드와 Pod에서 확인
node1$ curl -m3 -sS -o /dev/null https://1.1.1.1 && echo ok
ok                         # 노드 자체는 정상입니다.
$ kubectl exec netshoot -- curl -m3 -sS https://1.1.1.1
curl: (28) Connection timed out
node1$ sudo tcpdump -ni eth0 host 1.1.1.1 -c 2
IP 10.244.1.9.51234 > 1.1.1.1.443: Flags [S]
# 출발지가 Pod IP입니다. SNAT이 적용되지 않았습니다.
node1$ sysctl net.ipv4.ip_forward
net.ipv4.ip_forward = 1
CNI별 SNAT 규칙 (masquerade가 꺼진 경우)
$ sudo iptables -t nat -S FLANNEL-POSTRTG
iptables: No chain/target/match by that name.   # Flannel
$ sudo iptables -t nat -S cali-nat-outgoing
-N cali-nat-outgoing             # Calico: MASQUERADE 규칙 없음
$ calicoctl get ippool -o yaml | grep natOutgoing
  natOutgoing: false
$ cilium-dbg status | grep Masquerading
Masquerading:   Disabled        # Cilium

실패한 통신 단계를 먼저 확인하고, 그 단계의 담당 컴포넌트를 CNI별 명령으로 확인합니다.

영향 범위

전체 클러스터, 특정 노드, 특정 Pod, 특정 목적지 중 어디인지 먼저 확인합니다. 범위에 따라 확인할 컴포넌트가 달라집니다.

통신 단계

Pod 네트워크 생성부터 DNS 이름 조회까지 순서대로 확인하고, 처음 실패한 단계의 담당 컴포넌트를 확인합니다.

패킷 확인

로그만으로 판단하기 어려우면 양쪽 노드에서 패킷을 캡처해서 어디서 사라지는지 확인합니다.

장애를 사전에 줄이는 방법
IP 풀과 노드별 블록 사용률이 80%에 도달하면 알림을 보냅니다. 노드 NIC와 Pod의 MTU 기준을 문서로 정리합니다. CNI가 사용하는 포트와 프로토콜을 방화벽 정책에 명시합니다. CoreDNS의 지연과 오류율을 모니터링하고, 필요하면 NodeLocal DNSCache를 사용합니다. CNI 업그레이드는 노드 단위로 순차 적용하고, 단계별 확인으로 검증합니다. NetworkPolicy를 변경할 때는 드롭 로그나 Hubble로 영향을 미리 확인합니다.
