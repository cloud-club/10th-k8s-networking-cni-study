기존 인프라와 Kubernetes의 차이

기존 인프라에서는

  • 서버는 한 번 만들면 몇 년 동안 그대로 있다. IP도 고정이다.
  • 그래서 IP를 기준으로 Fortigate 정책을 만들고, 스위치 포트를 할당하고, NetScaler에 VIP를 등록하면 끝이다. 변경이 생기면 사람이 작업 요청서를 받아서 처리한다.

Kubernetes에서는

  • Pod가 하루에도 수십, 수백 번 생겼다가 없어진다. 다시 뜰 때마다 IP가 바뀐다.
  • 이걸 사람이 매번 방화벽 정책, 라우팅, LB 멤버에 반영하는 건 불가능하다.

그래서 Pod가 생기는 순간 자동으로 IP를 주고, 선을 꽂고, 라우팅을 잡고, LB 멤버에 넣고, 방화벽 정책까지 적용하는 소프트웨어가 필요하다. 이 역할을 하는 플러그인을 CNI라고 부르고, Cilium은 CNI 중 하나다. (Week 4의 Flannel, Calico도 같은 종류다.)

한 줄 정의

Cilium = 모든 Node의 Linux 커널 안에 설치되는 "소프트웨어 스위치 + 라우터 + L4 로드밸런서 + 방화벽 + 트래픽 모니터". 이 기능들을 iptables가 아니라 eBPF로 구현한다. 2023년 CNCF 졸업(Graduated) 프로젝트가 되었다.

1. Cilium Architecture

Cilium 구조는 네트워크 엔지니어에게 익숙한 Control Plane / Data Plane 분리로 보면 가장 이해하기 쉽다.

  • Control Plane (유저스페이스): Kubernetes에서 Pod, Service, 정책 정보를 받아서 "무엇을 할지" 정한다.
  • Data Plane (커널): 각 Pod의 인터페이스와 Node NIC에 붙은 eBPF 프로그램이 실제 패킷을 처리한다.

기존 인프라 관점 기존 구조에서는 모든 트래픽이 중앙의 Fortigate와 NetScaler를 거친다. Cilium에는 중앙 장비가 없고, 모든 Pod의 "포트"마다 작은 방화벽 + LB가 붙어 있다. 트래픽이 중앙 장비까지 갔다 오지 않고, 보내는 Node의 커널 안에서 정책 판단과 VIP 변환이 끝난다.

질문 1. cilium-agent Pod가 재시작되는 동안 기존 Pod끼리의 통신은 끊길까?

끊기지 않는다. 패킷을 처리하는 것은 커널에 이미 붙어 있는 eBPF 프로그램과 Map이고, agent는 그 내용을 관리할 뿐이다. 재시작하는 동안에는 새 Pod, 새 정책, Service 변경이 반영되지 않는다. Fortigate 관리 화면이 멈춰도 이미 내려간 정책으로 트래픽이 계속 처리되는 것과 같다.

2. eBPF 기본 개념 및 Hook

eBPF란

eBPF(extended Berkeley Packet Filter)는 커널을 다시 컴파일하거나 커널 모듈을 넣지 않고, 커널 안의 정해진 지점(Hook)에 검증된 작은 프로그램을 붙여서 실행하는 기술이다. 1992년에 만들어진 BPF(패킷 필터)를 확장한 것이고, 커널 안의 작은 가상 머신에서 실행된다.

기존 인프라 비유: eBPF ≈ "Linux 커널용 iRule / NetScaler 정책" NetScaler에서는 Responder나 Rewrite 정책을 바인드 포인트에 붙이고, F5에서는 iRule을 HTTP_REQUEST 같은 이벤트에 붙인다. 장비 펌웨어를 바꾸지 않고도 정해진 지점에 내가 만든 로직을 끼워 넣는 방식이다. eBPF는 이 방식을 Linux 커널에 적용한 것이다.

NetScaler / F5eBPF
장비 펌웨어Linux 커널
정책 바인드 포인트 / iRule 이벤트Hook (패킷 수신 시점, 송신 시점, connect() 호출 시점 등)

정책 저장 시 문법 검사Verifier. 훨씬 엄격해서, 무한 루프나 범위 밖 메모리 접근처럼 커널이 죽을 수 있는 코드는 아예 거부한다.
Data Group / String MapeBPF Map (커널과 유저스페이스가 함께 쓰는 key-value 테이블)

eBPF가 없을 때는 커널에 기능을 추가하려면 커널 개발 커뮤니티에 반영되기를 몇 년 기다리거나(벤더 펌웨어 업데이트를 기다리는 것과 같다), 커널 모듈을 직접 넣어야 했다(검증 안 된 서드파티 드라이버를 설치하는 것과 같아서, 잘못되면 서버가 다운된다). eBPF는 그 사이에 있는 안전한 확장 슬롯이다.

프로그램이 커널에 들어가는 과정

C 코드 ──clang/LLVM──▶ BPF 바이트코드
                          │ bpf() 시스템 콜로 로드
                          ▼
                   Verifier (안전성 검사) ── 실패하면 거부
                          │ 통과
                          ▼
                   JIT 컴파일 (네이티브 기계어)
                          │
                          ▼
                   Hook에 attach → 이벤트(패킷 등)마다 실행
                          ⇅
                   eBPF Map ⇄ 유저스페이스 (cilium-agent)

핵심은 로직은 커널 안의 프로그램이 처리하고, 규칙의 내용은 유저스페이스가 Map에 써 넣는다는 점이다. Service나 정책이 바뀌어도 프로그램을 다시 로드하지 않고 Map 엔트리만 바꾸면 된다.

네트워크 Hook 위치

Week 1에서 본 Netfilter Hook과 같은 축에 놓고 보면, 수신 쪽 eBPF Hook(XDP, tc ingress)은 Netfilter보다 앞에 있고, 소켓 Hook은 패킷이 생기기도 전에 있다. 송신 쪽 tc egress는 POSTROUTING 다음, NIC로 나가기 직전에 실행된다.

질문 2. Cilium이 Service 규칙을 바꿀 때 eBPF 프로그램을 다시 로드하지 않아도 되는 이유는?

규칙의 내용(VIP → Backend 목록 등)이 프로그램이 아니라 Map에 들어 있기 때문이다. 프로그램은 "Map을 조회해서 그 결과대로 처리하라"는 로직만 갖고 있다. agent가 Map 엔트리만 바꾸면 바로 다음 패킷부터 새 규칙이 적용된다.

3. Cilium Datapath

Datapath는 "패킷이 실제로 어떤 인터페이스와 어떤 eBPF 프로그램을 거쳐 가는가"이다.

Node 안의 인터페이스

인터페이스역할붙는 eBPF 프로그램기존 인프라 비유
lxcXXXXPod veth의 호스트 쪽 끝. Pod마다 하나bpf_lxc스위치 포트 + 포트별 ACL
cilium_host / cilium_net서로 연결된 veth 쌍. cilium_host의 IP가 Pod들의 기본 게이트웨이bpf_hostSVI (VLAN 인터페이스, 게이트웨이)
cilium_vxlan터널 모드에서 Node 간 VXLAN 캡슐화 (UDP 8472). Geneve(UDP 6081)도 선택 가능bpf_overlayVTEP
eth0Node의 물리 NICbpf_host업링크 포트

Week 4의 Flannel은 cni0 브리지에 모든 Pod를 연결했다. Cilium에는 L2 브리지가 없다. 각 lxc에 붙은 eBPF 프로그램과 라우팅이 패킷을 목적지로 바로 보낸다. 스위치 없이 포트마다 라우팅과 ACL을 하는 구조라고 보면 된다.

Pod → Service → 다른 Node의 Pod

그림 3. Pod A → Service → 다른 Node의 Pod B. 참고: Arthur Chiao, Life of a Packet in Cilium / Cilium Docs, Life of a Packet

  • 같은 Node의 Pod끼리: bpf_lxc가 목적지가 같은 Node의 Pod인 것을 확인하면, 정책을 검사한 뒤 목적지 Pod 쪽으로 바로 redirect한다. Netfilter를 거치지 않는다.
  • 다른 Node로: 터널 모드는 cilium_vxlan으로 캡슐화하고, 네이티브 라우팅 모드는 언더레이가 Pod CIDR을 알고 있어야 한다(기본 경로 라우터 또는 BGP, auto-direct-node-routes). Week 4의 Overlay와 Underlay 비교와 같은 선택지다.
  • L7 정책이 있으면: 패킷이 Node의 Envoy 프록시를 한 번 거친다. L7 정책이 없으면 프록시를 거치지 않는다.
  • BPF Host Routing: 커널이 지원하고 eBPF kube-proxy replacement와 eBPF masquerade(bpf.masquerade=true)를 함께 쓰면 자동으로 켜진다(cilium-dbg status의 Host Routing: BPF). 이때는 호스트의 상위 네트워크 스택과 Netfilter를 건너뛰고 eBPF가 NIC로 바로 보낸다. 오래된 자료(Cilium 1.8, 커널 4.19 기준)의 그림보다 경로가 더 짧다.

질문 3. Pod가 보내는 패킷인데, 자료에서는 왜 "lxc의 ingress"에서 처리한다고 할까?

방향을 호스트 쪽 veth 끝(lxc) 기준으로 보기 때문이다. Pod의 eth0에서 나간 패킷은 veth 쌍의 반대편인 lxc로 "들어온다". 그래서 Pod 입장의 egress가 lxc 입장에서는 tc ingress다. 스위치 포트 ACL에서 "서버가 보낸 트래픽 = 포트 inbound"인 것과 같다.

4. kube-proxy Replacement

기존: kube-proxy + iptables (Week 2 복습)

kube-proxy는 Service마다 iptables 규칙을 만든다. Pod가 ClusterIP로 보낸 패킷은 Netfilter의 PREROUTING/OUTPUT에서 DNAT되어 Backend Pod IP로 바뀐다. Service와 Endpoint가 많아지면 규칙이 수만 줄이 되고, 순차 매칭과 전체 재작성 문제가 생긴다.

Cilium: 같은 일을 더 앞에서, Map으로

트래픽처리 위치방식
클러스터 안 Pod → ClusterIPcgroup socket hook (Socket-LB)connect() 시점에 소켓의 목적지를 Backend Pod IP로 바꾼다. 이후 패킷마다 NAT할 필요가 없다.
외부 → NodePort / LoadBalancerNode NIC의 tc (bpf_host), 선택적으로 XDPBPF Map에서 Backend를 찾아 DNAT. 기본은 SNAT 모드이고, 응답이 Backend에서 클라이언트로 바로 가는 DSR 모드도 있다.
Socket-LB를 쓸 수 없는 경우bpf_lxc (tc)패킷 단위로 DNAT (그림 3의 ①)

기존 인프라 비유 기존에는 클라이언트가 NetScaler VIP로 보내면 중앙 장비가 멤버를 고른다. Cilium의 Socket-LB는 클라이언트 서버 안에서 연결을 맺는 순간 멤버를 골라서, 처음부터 멤버 IP로 연결하게 한다. 모든 Node에 작은 NetScaler가 하나씩 있고, 그것이 연결 시점에만 동작한다고 보면 된다.

설정과 확인

# Helm 설치 시 kube-proxy 대체 활성화
helm install cilium cilium/cilium -n kube-system \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=<API_SERVER_IP> --set k8sServicePort=6443

# 상태 확인
kubectl -n kube-system exec ds/cilium -- cilium-dbg status | grep KubeProxyReplacement

# Service → Backend 테이블 (iptables-save 대신 보는 것)
kubectl -n kube-system exec ds/cilium -- cilium-dbg service list
kubectl -n kube-system exec ds/cilium -- cilium-dbg bpf lb list

kube-proxy가 없으면 Cilium이 API Server의 ClusterIP를 쓸 수 없다. 그래서 k8sServiceHost와 k8sServicePort로 API Server 주소를 직접 알려준다.

질문 4. Socket-LB 환경에서 Pod 안에서 tcpdump를 하면 목적지가 ClusterIP로 보일까, Backend Pod IP로 보일까?

Backend Pod IP로 보인다. connect() 시점에 이미 목적지가 바뀌었기 때문에, 패킷은 처음부터 Pod IP를 목적지로 만들어진다. 반면 앱이 getpeername()으로 상대 주소를 물어보면 ClusterIP를 돌려준다. 앱 입장에서는 여전히 ClusterIP로 연결한 것처럼 보이게 하는 것이다. 장애 분석 시 iptables 규칙이나 패킷 캡처에서 ClusterIP를 찾으면 안 되는 이유다.

참고: Cilium Docs - Kubernetes Without kube-proxy

5. NetworkPolicy / Identity

왜 IP 기반 정책이 안 되는가

Pod IP는 재시작할 때마다 바뀌고, 같은 역할의 Pod가 수십 개로 늘었다 줄었다 한다. IP 기반 규칙은 변경될 때마다 모든 Node의 규칙을 고쳐야 한다. 그래서 Cilium은 정책을 IP가 아니라 라벨(app=web, app=db)로 쓴다.

Identity: 라벨 묶음에 붙인 번호

  1. Pod가 생기면 agent가 Pod의 보안 관련 라벨 묶음(예: app=web, ns=shop)을 보고 숫자 Identity를 할당한다. 라벨이 같은 Pod는 Identity를 공유한다.
  2. agent는 IP → Identity 대응표(ipcache Map)와 Endpoint별 정책 Map(허용되는 Identity와 Port 목록)을 커널에 써 넣는다.
  3. 패킷이 오면 eBPF가 출발지 Identity를 확인하고 정책 Map을 조회해서 허용/차단을 판정한다. 터널 모드에서는 보내는 Node가 캡슐화 헤더에 출발지 Identity를 실어 보내고, 네이티브 라우팅에서는 받는 Node가 출발지 IP로 ipcache를 조회한다.

Pod가 10개에서 100개로 늘어도 라벨이 같으면 Identity는 하나다. 정책 Map을 고칠 필요 없이 ipcache에 "새 IP → 같은 Identity"만 추가하면 된다.

기존 인프라 비유 Fortigate에서 IP를 직접 쓰는 대신 동적 주소 객체(SDN Connector로 자동 갱신되는 주소 그룹)로 정책을 쓰는 것과 같다. 정책은 "WEB 그룹 → DB 그룹 3306 허용" 한 줄이고, 그룹 멤버 IP는 자동으로 바뀐다. Identity는 그 주소 그룹에 붙은 번호이고, 패킷마다 IP 대신 그 번호로 매칭한다.

정책 예시 (L3/L4 + L7)

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: db-allow-web
  namespace: shop
spec:
  endpointSelector:
    matchLabels:
      app: db                 # 이 정책이 보호하는 대상
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: web              # IP가 아니라 라벨로 출발지 지정
    toPorts:
    - ports:
      - port: "3306"
        protocol: TCP
---
# L7 예시: api Pod에는 GET /public/* 만 허용 (Envoy가 처리)
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: api-l7
  namespace: shop
spec:
  endpointSelector:
    matchLabels: { app: api }
  ingress:
  - fromEndpoints:
    - matchLabels: { app: web }
    toPorts:
    - ports: [{ port: "8080", protocol: TCP }]
      rules:
        http:
        - method: GET
          path: "/public/.*"

기본 동작 (default 모드)

  • Pod는 처음에 아무 제한 없이 통신한다.
  • 어떤 정책이 그 Pod를 선택하는 순간, 정책에 있는 방향(ingress/egress)은 default deny가 되고 허용한 것만 통과한다.
  • Kubernetes 표준 NetworkPolicy도 그대로 지원한다. CiliumNetworkPolicy는 L7, DNS(FQDN) 기반 규칙 등을 추가로 지원한다.

Fortigate의 "마지막 줄 implicit deny"와 달리, 정책이 하나도 선택하지 않은 Pod는 모두 허용 상태다. 정책을 처음 적용할 때는 그 Pod의 해당 방향이 갑자기 default deny로 바뀌므로 필요한 트래픽(DNS 등)을 빠뜨리지 않았는지 확인해야 한다.

# Identity와 정책 상태 확인
kubectl -n kube-system exec ds/cilium -- cilium-dbg endpoint list
kubectl -n kube-system exec ds/cilium -- cilium-dbg identity list
kubectl -n kube-system exec ds/cilium -- cilium-dbg bpf ipcache list
kubectl -n kube-system exec ds/cilium -- cilium-dbg bpf policy get <ENDPOINT_ID>

질문 5. 기존 인프라처럼 IP 기반 방화벽 정책을 Kubernetes에 그대로 쓰기 어려운 이유는?

Pod IP가 고정되지 않기 때문이다. Pod가 재시작하거나 늘어날 때마다 IP가 바뀌므로 정책을 계속 고쳐야 하고, 모든 Node에 다시 배포해야 한다. 라벨 기반 Identity를 쓰면 정책은 그대로 두고 IP와 Identity의 대응만 자동으로 갱신된다.

6. Hubble Overview

Hubble은 Cilium의 관찰(Observability) 도구다. 별도의 패킷 미러링이나 에이전트 없이, Cilium의 eBPF datapath가 패킷을 처리하면서 남기는 이벤트를 그대로 모아서 보여준다.

구성요소하는 일기존 인프라 비유
Hubble Server각 Node의 cilium-agent에 내장. eBPF 이벤트를 flow로 변환해서 gRPC로 제공장비별 로그 / diagnose debug flow
hubble-relay모든 Node의 Hubble Server를 모아서 클러스터 전체 flow를 제공FortiAnalyzer (로그 수집)
hubble CLIflow 조회, 필터링로그 검색
hubble-ui서비스 간 연결 관계(서비스 맵)와 flow를 그래픽으로 표시FortiView

무엇을 볼 수 있나

  • L3/L4: 출발지/목적지 Pod, Identity, Port, TCP 플래그, 판정(FORWARDED / DROPPED)과 차단 사유
  • L7 (L7 가시성 또는 정책이 켜진 경우): HTTP 메서드, 경로, 응답 코드, DNS 질의
  • 서비스 맵: 어떤 서비스가 어떤 서비스를 호출하는지
# 차단된 트래픽만 보기
hubble observe --verdict DROPPED

# 특정 Pod로 가는 트래픽 보기
hubble observe --to-pod shop/db-5f6b9c --follow

# 출력 예시 (형식 설명용)
Oct  1 05:12:03.123: shop/web-7d9c:51234 (ID:12345) -> shop/db-5f6b:3306 (ID:23456) policy-verdict:L3-L4 INGRESS ALLOWED (TCP Flags: SYN)
Oct  1 05:12:09.456: shop/batch-6c1a:40022 (ID:34567) <> shop/db-5f6b:3306 (ID:23456) Policy denied DROPPED (TCP Flags: SYN)

기존 인프라 비유 Fortigate의 diagnose debug flow는 "이 패킷이 몇 번 정책에 걸려서 허용/차단됐다"를 보여준다. Hubble은 이것을 클러스터의 모든 Node에서 항상 수집하고, IP 대신 Pod 이름과 Identity로 보여준다. Pod IP가 계속 바뀌는 환경에서는 IP로 찍힌 로그만으로는 누가 보냈는지 알 수 없기 때문에 이 차이가 중요하다.

참고: Cilium Docs - Network Observability with Hubble

참고: Cilium Docs - Component Overview (Hubble)

정리 과제

1. eBPF가 네트워크 처리에 들어가는 위치

  • XDP: NIC 드라이버 단계. skb가 만들어지기 전이라 가장 빠르다. NodePort 가속, 대량 DROP에 쓴다.
  • tc ingress / egress: 각 인터페이스(lxc, eth0, cilium_host, cilium_vxlan)에 붙는다. Cilium의 메인 datapath로 정책, NAT, 라우팅, 캡슐화를 처리한다.
  • cgroup socket hook: connect()/sendmsg()/recvmsg() 시스템 콜 시점. 패킷이 생기기도 전에 ClusterIP를 Backend IP로 바꾼다(Socket-LB).

XDP와 tc ingress는 수신 경로에서 Netfilter보다 앞이고, 소켓 Hook은 패킷이 생기기 전이며, tc egress는 송신 경로의 마지막(POSTROUTING 뒤)이다. 정책 판정과 Service 변환이 이 지점들에서 끝나기 때문에(BPF Host Routing을 쓰면 호스트의 Netfilter도 우회), Cilium 트래픽은 대부분 iptables 규칙의 영향을 받지 않는다. (그림 2)

2. Cilium이 기존 CNI와 다른 점

관점기존 CNI (Flannel, iptables 기반 구성)Cilium
패킷 처리Linux 브리지 + Netfilter(iptables) 규칙인터페이스마다 붙은 eBPF 프로그램 (브리지 없음)
규칙 저장 / 조회체인을 순서대로 검사, 변경 시 전체 재작성Map 해시 조회, 엔트리 단위 갱신
Servicekube-proxy가 iptables/IPVS로 DNATkube-proxy 없이 Socket-LB / tc / XDP에서 처리
정책 기준IP / Port (Flannel은 정책 자체가 없음)라벨 기반 Identity, L7(HTTP, DNS)까지
가시성별도 도구 필요 (tcpdump, conntrack)Hubble이 datapath 이벤트를 그대로 보여줌

한 문장으로 하면, 기존 CNI는 커널이 원래 가진 기능(브리지, iptables)을 설정해서 쓰고, Cilium은 처리 로직 자체를 eBPF 프로그램으로 커널에 넣는다. Calico도 eBPF 데이터플레인 모드를 지원하므로, 정확히는 "CNI 종류"보다 "iptables 데이터플레인 vs eBPF 데이터플레인"의 차이다.

3. 트래픽 관찰과 정책 적용이 어떻게 연결되는지

정책을 판정하는 곳과 관찰 데이터가 생기는 곳이 같은 eBPF 프로그램이다. 그래서 Hubble에 보이는 판정 결과는 실제로 패킷에 적용된 결과 그 자체다.

그림 4. 정책 적용(①~③)과 관찰(④)이 같은 datapath에서 이어지는 흐름

  • eBPF 프로그램은 패킷을 허용하거나 버릴 때 그 결과(판정, 사유, Identity)를 이벤트로 남긴다. Hubble은 이 이벤트를 수집한다.
  • 정책이 IP가 아니라 Identity 기준이므로, Hubble flow에도 Pod 이름과 라벨이 그대로 찍힌다. "어떤 서비스가 어떤 서비스에 막혔는지"를 바로 알 수 있다.
  • 운영에서는 "Hubble로 실제 통신 관계 파악 → 그것을 근거로 정책 작성 → DROPPED flow로 누락 확인"이라는 순서로 정책을 만든다. Fortigate에서 로그를 보고 정책을 다듬는 것과 같은 작업을 Pod 단위로 하는 것이다.
