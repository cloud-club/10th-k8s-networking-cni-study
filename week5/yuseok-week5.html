Cilium & eBPF

Cilium을 중심으로 eBPF 기반 네트워킹을 이해합니다. kube-proxy 대체, 정책 처리, 가시성 기능까지 포함해 Cilium의 데이터 경로를 살펴봅니다.

Cilium

Cilium이란?

컨테이너로 돌아가는 서비스들 사이의 네트워크 연결을 투명하게 보호하는 오픈소스 소프트웨어로, 리눅스 커널의 eBPF를 사용하기 때문에 애플리케이션 코드를 고치지 않고도 보안 정책을 적용할 수 있습니다.

Hubble이란?

Cilium과 eBPF 위에 만든 분산 관측(observability) 플랫폼으로, 네 가지 질문에 답해 줍니다.

영역알 수 있는 것
서비스 의존성어떤 서비스가 어떤 서비스와 통신하는지, HTTP 호출 흐름
네트워크 모니터링연결이 실패했는지, L4(TCP)와 L7(HTTP) 어느 단계에서 문제가 생겼는지
애플리케이션 모니터링HTTP 응답 코드 비율, 지연 시간
보안 관측정책 때문에 차단된 연결, 정책 위반

왜 Cilium과 Hubble인가?

기존 방화벽은 IP 주소 기반으로 규칙을 정합니다. 하지만 쿠버네티스에서는 IP가 계속 바뀌기 때문에 IP 기반 규칙이 잘 맞지 않습니다. Cilium은 이 문제를 아래처럼 해결합니다.

  • IP 대신 파드/서비스의 신원(identity, 레이블 기반)으로 정책 적용
  • HTTP 같은 L7 수준 필터링까지 지원 (L3~L7)
  • eBPF 덕분에 규모가 커져도 성능 유지
예시: app=frontend 파드는 app=backend 파드에 GET /api/* 요청만 보낼 수 있다.

주요 기능 개요

기능내용
CNI 플러그인Pod 네트워킹을 제공하며 터널 기반(VXLAN/Geneve)과 Native Routing을 지원한다. 추가적으로 BGP Control Plane과 L2 Announcements를 통해 Pod/Service를 외부 네트워크에 노출할 수 있다.
로드밸런싱클러스터 내부 트래픽은 connect() 호출 순간 목적지를 백엔드 파드 IP로 한 번만 바꿔 kube-proxy를 대체하고, 외부 유입 트래픽은 TC(선택적으로 XDP 가속)에서 분산하며 DSR과 Maglev 옵션으로 효율과 안정성을 높입니다.
Cluster Mesh여러 클러스터를 하나처럼 연결해서, 다른 클러스터의 서비스도 로컬처럼 쓰고(장애 시 자동 전환 포함), IP가 아닌 신원 기반 보안 정책을 클러스터 전체에 똑같이 적용
네트워크 정책레이블이 같은 파드 그룹에 하나의 신원을 붙이고 패킷과 함께 전달해서, 받는 쪽에서 신원만 확인합니다. 그래서 파드가 늘거나 IP가 바뀌어도 정책을 고칠 필요가 없고, 여기에 DNS, L7, CIDR 정책까지 더해 L3부터 L7까지 세밀하게 제어할 수 있습니다.
서비스 메시파드마다 사이드카 프록시를 붙이지 않고, L3/L4는 eBPF로, L7은 노드당 Envoy 하나로 처리해서 서비스 메시 기능(암호화, L7 정책, Gateway API 기반 라우팅)을 더 적은 비용과 복잡성으로 제공
관측eBPF로 패킷을 처리하는 그 자리에서 정보를 함께 수집해서, Hubble로 신원 기반 트래픽 흐름과 서비스 맵을 보여 주고, Prometheus/Grafana로 메트릭과 알림을 제공하며, 패킷이 버려진 이유까지 알려 줍니다.

아키텍처 흐름

1. 쿠버네티스에서 파드 생성 → Plugin이 Cilium Daemon에 알림
2. Daemon이 Policy Repository에서 정책 확인
3. Daemon이 그 파드에 맞는 BPF 코드 생성·컴파일 (Code Generation)
4. 바이트코드를 커널에 주입 (Bytecode injection)
5. 커널에서 BPF 프로그램이 그 컨테이너의 트래픽 처리
6. CLI와 Monitor로 상태와 트래픽 확인

가운데 Bytecode injection: Daemon에서 만든 바이트코드를 커널에 주입하는 단계

C 코드 생성 → clang/LLVM 컴파일 → BPF 바이트코드 → 커널에 로드
→ 검증기 통과 → JIT으로 기계어 변환 → 실행

Cilium 구성 요소

  1. Agent (cilium-agent)
    • 모든 노드에서 하나씩 실행되며 쿠버네티스나 API를 통해 설정을 받습니다.
    • 각 노드에서 쿠버네티스의 설정과 이벤트를 받아, 그에 맞게 eBPF 프로그램과 BPF 맵을 관리하는 노드별 관리자
  2. Debug Client (CLI, cilium-dbg)
    • Cilium 에이전트와 함께 설치되는 명령줄 도구. 같은 노드에서 실행 중인 Cilium 에이전트의 REST API와 통신하여 로컬 에이전트의 상태를 확인할 수 있고, eBPF 맵에 직접 접근해서 상태를 검증하는 도구를 제공합니다.
    • 노드 안에서 그 노드 에이전트의 상태와 실제 BPF 맵을 직접 들여다보는 디버깅 도구
  3. Operator
    • IP 대역 배분, 정리 작업처럼 클러스터 전체에서 한 번만 하면 되는 관리 업무를 맡고, 패킷 처리 경로에는 없어서 잠시 멈춰도 기존 트래픽은 유지됩니다. 다만 설정에 따라 새 파드의 IP 할당이 늦어지거나, etcd를 쓰는 경우 에이전트가 재시작될 수 있습니다.
  4. CNI Plugin (cilium-cni)
    • 파드가 생성되거나 삭제될 때 kubelet이 실행하는 표준 CNI 플러그인이고, 실제 네트워크 구성은 같은 노드의 cilium-agent에게 요청해서 처리하게 하는 연결 창구

기반 기술

eBPF

eBPF는 패킷 필터에서 출발해 맵과 다양한 동작이 추가된 커널 내 프로그램 실행 환경이고, 검증기로 안전성을, JIT으로 성능을 확보하며 여러 훅에서 실행됩니다. Cilium은 커널이 지원하는 기능을 자동으로 확인해서 가능한 한 최신 기능을 활용합니다.

데이터 저장소

에이전트들이 정책, 신원(identity) 같은 정보를 공유하는 곳입니다.

방식설명
Kubernetes CRD (기본값)쿠버네티스 API에 Cilium 전용 리소스(CiliumNetworkPolicy, CiliumIdentity 등)를 만들어 저장
Key-value store (etcd)대규모 클러스터에서 확장성을 높이기 위한 선택 사항. 쿠버네티스 API 서버의 부하를 줄여 줌

Cilium 에이전트들은 신원, 엔드포인트, 노드 정보를 서로 공유해야 하고, 기본적으로는 쿠버네티스 CRD에 저장해 전파합니다. 클러스터가 아주 크면 etcd를 직접 쓰는 방식으로 API 서버 부하를 줄이고 전파를 더 효율적으로 만들 수 있습니다.

Cilium에서 Life of a Packet의 의미

아래 그림들은 패킷이 실제로 지나가는 길(데이터 플레인)만 보여 줍니다. Cilium 전체는 이렇게 동작합니다.

[쿠버네티스 API] 파드, 서비스, NetworkPolicy 정보
      ↓
[cilium-agent] (각 노드의 사용자 공간 프로그램)
  - C로 된 BPF 코드를 컴파일해 커널에 로드
  - 정책, 서비스 정보를 BPF 맵에 기록
      ↓
[커널] 그림 속 bpf_* 프로그램들이 맵을 참고해 패킷 처리
  • C → BPF 바이트코드 → JIT: cilium-agent가 BPF 프로그램을 컴파일하고 로드합니다.
  • 검증기: 로드할 때 커널이 안전성을 검사합니다.
  • 원자적 업데이트: 정책이 바뀌면 트래픽을 끊지 않고 프로그램을 교체합니다.
  • 맵: 파드 IP, 정책, 서비스 백엔드 목록 등을 저장하고 사용자 공간과 커널이 함께 씁니다.

그림 밖에서도 Cilium은 eBPF를 더 쓰고 있습니다.

  • kube-proxy 대체: 소켓 단계(cgroup 훅)에서 서비스 IP를 바로 백엔드 IP로 바꿔서 iptables 없이 로드밸런싱
  • Hubble: eBPF로 패킷 흐름을 관찰해서 네트워크 가시성 제공
  • Tetragon: eBPF로 프로세스, 파일 접근 등 보안 이벤트 추적
아래 datapath 그림은 Cilium v1.13 기준입니다. 현재 문서(1.20)와 세부 구현은 조금 다를 수 있습니다.

같은 노드의 파드 간

  • 커널 스택을 일부 우회하고 파드 간에 전달하여 가장 효율적인 경로
  • L7 정책이 있을 때만 커널 스택과 프록시(Envoy)를 거침 (egress/ingress 모두 가능)

파드에서 외부로

  • bpf_lxc가 egress 정책 검사
  • 라우팅과 SNAT(masquerade) 때문에 커널 스택을 활용
  • 선택 기능: L7 정책, IPsec 암호화, Overlay 캡슐화(클러스터 내부 트래픽용)

외부나 다른 노드에서 파드로

  • XDP(bpf_xdp)로 가장 앞단에서 필터링
  • 터널이면 디캡슐화, IPsec이면 복호화
  • bpf_host가 목적지를 찾고 bpf_lxc가 ingress 정책 검사
  • 선택 기능: Standalone 로드밸런서(bpf_lb), L7 정책

자주 나오는 BPF 프로그램

eBPF 기본 개념 및 Hook

C → BPF 바이트코드 → 기계어

  • C로 쓰는 이유: BPF 명령어는 어셈블리 수준이라 직접 쓰기 어려움
  • 바이트코드를 거치는 이유
    1. 커널이 실행 전에 안전성 검증을 하려면 단순한 형식이 필요
    2. CPU 독립성 (각 노드의 JIT이 x86/ARM에 맞게 변환)

구성 요소

요소역할
검증기무한 루프, 잘못된 메모리 접근 차단
JIT바이트코드를 CPU 기계어로 변환해 네이티브 속도로 실행
맵커널과 사용자 공간이 데이터를 공유하는 저장소 (정책, 신원, 서비스 백엔드)
헬퍼 함수커널이 제공하는 기능 (리다이렉트, 라우팅 조회 등)

= eBPF가 네트워크 처리에 들어가는 위치

[NIC] → XDP → (sk_buff 생성) → TC ingress → 커널 스택 → 소켓 ← cgroup(connect)
                                  TC egress ←───────────────┘
Hook위치Cilium에서의 용도
XDPNIC 드라이버, 가장 앞단DDoS 필터링(bpf_xdp), north-south 로드밸런싱 가속
TC드라이버 다음, 커널 스택 앞정책 검사, 전달 (bpf_lxc, bpf_host, bpf_overlay)

기타 특징

  • 원자적(atomic) 업데이트: 프로그램 교체 시 빈틈이 없어서 트래픽이 끊기지 않음
  • 안정적인 ABI: 커널 버전이 바뀌어도 잘 깨지지 않고, 서드파티 커널 모듈이 필요 없음
  • cBPF vs eBPF: cBPF는 패킷 필터 전용(tcpdump)이고, eBPF는 맵, 헬퍼, 다양한 훅이 추가된 확장 버전. 요즘 "BPF"는 대부분 eBPF를 뜻함

kube-proxy Replacement

Cilium은 kube-proxy가 하던 서비스 로드밸런싱(ClusterIP, NodePort, LoadBalancer, externalIPs)을 eBPF로 처리해서 kube-proxy 없이 클러스터를 운영할 수 있게 합니다.

NetworkPolicy / Identity

신원(Identity) 동작 방식

1. 레이블이 같은 파드 그룹 → 숫자 신원 하나 부여 (예: app=frontend → 12345)
2. 신원 정보를 CRD(또는 etcd)로 모든 노드에 공유
3. 패킷의 출발지 신원 확인
   - Overlay: 터널 헤더에 신원을 실어 보냄
   - 네이티브 라우팅: 받는 쪽이 ipcache 맵(IP → 신원)에서 조회
4. 받는 쪽 bpf_lxc가 "12345 허용?"만 확인
파드가 늘어나거나 IP가 바뀌어도 신원은 그대로라서 정책을 고칠 필요가 없음 (보안을 주소에서 분리)

질문

Q. Cilium이 로드밸런서를 대체할 수 있는데, 그럼 쿠버네티스 환경에서 우리가 사용하는 로드밸런서를 쓰지 않고 비용 절감이 가능할까?

온프레미스에서는 외부 로드밸런서를 줄이거나 대체해 비용 절감이 가능할 수 있고, 클라우드에서는 보통 CSP LoadBalancer와 Cilium을 함께 사용하되 개수를 줄이는 방식으로 비용을 절감할 수 있습니다.

다만 AWS NLB 같은 클라우드 LoadBalancer가 제공하는 공인 IP, 헬스체크, 멀티 AZ, 관리형 기능까지 항상 대체하는 것은 아닙니다.
