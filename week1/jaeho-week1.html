Kubernetes 컴포넌트 Overview

  • 클러스터 = Control Plane + Node(Worker) 두 영역
  • Control Plane → 결정·기록만 담당
  • Node → 실제 패킷 처리 담당

STEP 1Control Plane 구성 요소

컴포넌트역할네트워킹 관점 포인트
kube-apiserver클러스터의 유일한 진입점(REST API)Service·Endpoint·NetworkPolicy도 결국 etcd에 저장되는 상태값. apiserver 자체는 패킷을 처리하지 않음
etcd클러스터 상태를 저장하는 분산 key-value storePod IP, ClusterIP, Endpoint 목록 등 현재 상태의 단일 진실 공급원
kube-scheduler새 Pod를 어느 Node에 배치할지 결정스케줄링 시점엔 아직 IP 없음 — Node에 뜬 후에야 CNI가 IP 할당
controller-managerReplicaSet·Endpoint·Node 등 컨트롤러 루프 실행Endpoint Controller가 Selector와 매칭되는 Pod IP 목록 갱신 — kube-proxy가 참조하는 데이터의 출처
cloud-controller-manager클라우드 프로바이더 연동LoadBalancer 타입 Service 생성 시 실제 클라우드 LB 프로비저닝

STEP 2Node(Worker) 구성 요소

컴포넌트역할네트워킹 관점 포인트
kubelet해당 Node의 Pod 생명주기 관리 에이전트CRI로 컨테이너 실행, 네트워크 설정은 CNI 플러그인에 위임
Container Runtime실제 컨테이너 프로세스 생성·실행Pod의 pause 컨테이너가 먼저 뜨고 Network Namespace 소유 — 같은 Pod 내 다른 컨테이너는 join만
CNI 플러그인Pod에 실제 네트워크 인터페이스·IP 부여veth pair 생성, bridge 또는 라우팅 테이블 연결, IPAM까지 담당
kube-proxyClusterIP를 실제 Pod IP로 라우팅되게 규칙 구성기본은 iptables(또는 IPVS) — Endpoint 목록 watch하며 규칙 계속 갱신
  1. ① kubectl apply 요청 → apiserver 수신
  2. ② apiserver → kubelet: 이 Node에 배치된 Pod 정보 watch로 전달
  3. ③ kubelet → apiserver: Pod 상태·IP 보고
  4. ④ kubelet → Container Runtime(CRI): pause 포함 컨테이너 생성
  5. ⑤ kubelet → CNI 플러그인: netns·veth 연결, IP 할당
  6. ⑥ controller-manager(Endpoint) 변경 → kube-proxy가 watch해 iptables/IPVS 규칙 갱신

STEP 3Pod 생성 시 흐름

flow.txt

                → Endpoint Controller가 Service Endpoint 갱신
                → kube-proxy가 감지 후 iptables/IPVS 규칙 갱신

Q. kubelet은 CNI를 어떤 방식으로 호출할까?
A. Exec 방식 — 매번 프로세스를 fork해 CNI 바이너리를 실행하고 결과(JSON)를 받는 구조. CNI 실패 시 Pod는 ContainerCreating 상태로 남고, 재시도는 kubelet의 백오프 로직이 담당.
💡 핵심 한 줄 요약Control Plane은 상태를 결정하고 기록만 함. 실제 인터페이스 생성·IP 할당·규칙 삽입은 전부 Node 위 kubelet·CNI·kube-proxy 몫.

Network Namespace · veth · Bridge

  • netns·veth·bridge = Pod 격리 + 같은 Node 내 Pod 간 통신의 핵심 3요소

STEP 1Network Namespace(netns)

  • 커널 네트워크 스택(인터페이스·라우팅 테이블·iptables·ARP 테이블·소켓)을 namespace 단위로 완전 분리 가능
  • 호스트 기본값: default namespace 1개
  • 새 namespace 생성 시 loopback(lo)까지 새로 뜨는 독립 네트워크 환경

netns

network namespace

Pod = netns 1개. 같은 Pod 안 컨테이너들이 localhost로 통신 가능한 이유

veth pair

virtual ethernet

항상 쌍으로 생성되는 가상 랜케이블. 한쪽에 넣은 패킷이 반대쪽으로 그대로 나옴

bridge

linux bridge

소프트웨어 L2 스위치. MAC 학습으로 같은 Node의 Pod끼리 연결

terminal — netns 생성
ip netns add ns1
ip netns exec ns1 ip addr        # ns1 안엔 lo만 보임
ip netns exec ns1 ping 8.8.8.8    # 인터페이스 없어 실패

STEP 2veth pair 연결

  • veth 한쪽 끝 → Pod netns 안 eth0
  • veth 반대쪽 끝 → 호스트 root namespace, bridge에 연결
  • Pod가 보는 eth0 = veth pair의 절반, 나머지 절반(호스트 쪽 vethXXXXXX)이 bridge·라우팅 테이블에 연결
terminal — veth 생성
ip link add veth0 type veth peer name veth1
ip link set veth0 netns ns1              # veth0을 ns1 안으로 이동
ip netns exec ns1 ip link set veth0 name eth0 up
ip link set veth1 up                     # veth1은 호스트에 남음

STEP 3Linux Bridge와 같은 Node 내 통신

  • 여러 veth(호스트 쪽 끝)를 하나의 bridge에 연결
  • bridge가 MAC 주소 학습(learning)으로 같은 Node 위 Pod 간 L2 통신 성립
  • 대표 사례: Flannel cni0, Docker docker0
  1. ① Pod A → veth-A(호스트쪽) → cni0 진입, cni0이 출발 MAC 학습(FDB에 기록)
  2. ② cni0이 목적지 MAC으로 FDB 조회 → 일치하는 veth 포트(veth-B)로만 전달(스위칭)
💡 핵심 한 줄 요약netns가 격리를, veth가 연결을, bridge가 같은 Node 내 스위칭을 담당. 다른 Node로 넘어가는 순간 이 셋만으론 부족해 라우팅이 필요.

TCP/IP Stack · Routing · ARP

STEP 1TCP/IP 4계층과 캡슐화

계층예시Pod 통신에서의 의미
ApplicationHTTP, gRPC컨테이너 안 애플리케이션이 다루는 레벨
TransportTCP, UDPService의 port·targetPort가 위치하는 레벨
InternetIP, ICMP, ARPPod IP, Node IP, 라우팅 결정이 일어나는 레벨
LinkEthernetveth·bridge가 다루는 MAC 프레임 레벨
  • 나갈 때: 상위→하위로 헤더 계속 추가(캡슐화)
  • 받을 때: 하위→상위로 헤더 제거(역캡슐화)
  • 매 홉(veth·bridge·라우팅)마다 이 레벨에서 MAC·IP 재판단 → 여러 인터페이스를 거치는 것처럼 보이는 이유

STEP 2Routing — 라우팅 테이블

  • 패킷 송신 시 라우팅 테이블 참조 → 인터페이스·다음 홉(next hop) 결정
terminal — 라우팅 테이블 확인
ip route show
# default via 192.168.1.1 dev eth0
# 10.244.0.0/24 dev cni0 proto kernel scope link
# 10.244.1.0/24 via 192.168.1.11 dev eth0   ← 다른 Node의 Pod CIDR
  • Flannel(오버레이): 다른 Node Pod CIDR 경로를 VXLAN 인터페이스로 캡슐화
  • Calico(라우팅 기반): BGP로 라우팅 테이블 자체를 Node 간 광고(advertise)
오버레이 vs 언더레이 차이 = 라우팅 테이블 next hop이 터널 인터페이스냐 물리 인터페이스냐

STEP 3ARP — 주소 해석

  • IP = 논리 주소, MAC = 물리(링크 레벨) 주소
  • 같은 L2 세그먼트 통신 시 상대 IP → MAC 대응 필요 → ARP로 해결
브로드캐스트"이 IP 누구야?"
→
대상 응답자기 MAC으로 응답
→
캐시 저장ARP 테이블에 기록
terminal — ARP 캐시 확인
arp -n            # 또는 ip neigh show
  • 같은 Node(bridge 연결) Pod 간: ARP로 MAC 확인 후 직접 통신
  • 다른 Node Pod 간: 같은 L2 세그먼트 아님 → ARP 없이 곧바로 라우팅(next hop)으로 처리
Q. Calico BGP 모드처럼 bridge 없이 라우팅만 있는 경우, Pod의 게이트웨이 ARP는 누가 응답할까?
A. proxy ARP. veth 반대편(호스트 쪽)이 Pod netns 안 gateway IP에 대한 ARP 요청을 대신 받아 자신의 MAC으로 응답하도록 커널 옵션(proxy_arp)을 켜둔 구조.
💡 핵심 한 줄 요약같은 L2면 ARP로 MAC 찾아 직접 통신, 다른 세그먼트면 ARP 없이 라우팅 테이블의 next hop으로 넘어감 — 이 경계선이 오버레이 네트워크가 필요한 이유.
4

Netfilter · iptables

STEP 1Netfilter Hook Point

  • Netfilter = 커널 네트워크 스택 안 패킷 처리 훅 프레임워크
  • 패킷이 커널을 지나가는 5개 지점(Hook)에 규칙 적용
  1. ① 패킷이 Node NIC으로 수신
  2. ② PREROUTING 통과 — 목적지가 ClusterIP면 여기서 DNAT로 실제 Pod IP로 즉시 치환
  3. ③ 라우팅 결정 — 치환된 목적지가 로컬(이 host)이면 INPUT, 아니면 FORWARD로 분기
  4. ④ POSTROUTING 통과 — 나가는 인터페이스 기준으로 필요하면 SNAT(MASQUERADE) 적용
  5. ⑤ 최종 송신 — 이 시점 이후 패킷의 출발지·목적지는 이미 다 바뀐 상태
  • PREROUTING — 패킷이 들어오자마자, 라우팅 결정 전 (주로 DNAT)
  • INPUT — 목적지가 로컬(이 호스트)인 패킷
  • FORWARD — 목적지가 다른 곳이라 통과만 하는 패킷
  • OUTPUT — 로컬에서 생성돼 나가는 패킷
  • POSTROUTING — 나가기 직전, 마지막 지점 (주로 SNAT/MASQUERADE)

STEP 2iptables 테이블

테이블용도걸리는 Hook
filter패킷 허용/차단(방화벽)INPUT, FORWARD, OUTPUT
nat출발지/목적지 주소·포트 변환PREROUTING(DNAT), POSTROUTING(SNAT), OUTPUT
mangle패킷 헤더 수정(TTL, TOS 등)전체 훅
rawconntrack 추적 여부 결정PREROUTING, OUTPUT

STEP 3kube-proxy와의 연결고리

  • kube-proxy(iptables 모드) → Service 생성마다 nat 테이블에 규칙 체인 자동 생성
KUBE-SERVICES모든 ClusterIP 매칭
→
KUBE-SVC-XXXXService별 체인 점프
→
KUBE-SEP-XXXX확률적 랜덤 선택
→
DNAT선택된 Pod IP:Port
  • ClusterIP = 실제로 존재하지 않는 가상 주소
  • PREROUTING(또는 OUTPUT) 통과 시 iptables DNAT 규칙으로 실제 Pod IP로 치환
  • 응답 패킷은 conntrack(연결 추적 테이블)이 자동 역변환(un-DNAT) — 클라이언트는 Pod IP와 통신했다는 사실을 모름
terminal — 규칙 확인
iptables -t nat -L KUBE-SERVICES -n   # ClusterIP 매칭 규칙
iptables -t nat -L -n | grep -A2 KUBE-SEP  # 실제 DNAT 대상 확인
conntrack -L                          # un-DNAT 연결 추적 엔트리
💡 핵심 한 줄 요약IPVS 모드는 이 규칙을 iptables 체인이 아니라 커널 IPVS로 처리해, Service 수가 많아질수록 iptables 모드보다 성능이 우수.

전체 경로 한 장으로 몰아보기

  • Pod A → 다른 Node Pod B 통신 경로, 단계별 압축
  1. Pod A의 애플리케이션이 소켓에 데이터를 씀 → TCP/IP 스택이 헤더를 씌워 캡슐화
  2. Pod A netns의 eth0(veth 절반)으로 나감 → 반대쪽 veth가 호스트에서 수신
  3. 목적지가 다른 Node의 Pod CIDR임을 라우팅 테이블이 판단 → 같은 세그먼트가 아니라 ARP 없이 next hop으로
  4. PREROUTING 훅 통과 시점에 목적지가 로컬이 아니므로 FORWARD로 분기 — 단, Service 경유 트래픽이면 여기서 DNAT로 실제 Pod IP 결정
  5. 오버레이(VXLAN 캡슐화) 또는 언더레이(BGP 라우팅)를 거쳐 대상 Node로 물리 전달
  6. 대상 Node에서 라우팅 테이블이 목적지 Pod CIDR를 로컬 veth로 지정 → bridge 또는 라우팅으로 Pod B netns까지 전달
  7. Pod B의 TCP/IP 스택이 헤더를 벗겨내며 역캡슐화 → 애플리케이션 소켓 도달
