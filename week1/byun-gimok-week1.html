1. Kubernetes 컴포넌트 Overview

Kubernetes 클러스터는 Control Plane과 Worker Node로 나뉜다. Control Plane은 클러스터의 상태를 관리하고, Worker Node는 실제 Pod를 실행한다.

구분컴포넌트하는 일
Control Planekube-apiserverKubernetes API를 제공한다. 다른 컴포넌트는 API Server를 통해 클러스터 상태를 조회하거나 변경한다.
Control Planeetcd클러스터 상태 데이터를 저장한다.
Control Planekube-scheduler새로 생성된 Pod를 어느 Node에서 실행할지 정한다.
Control Planekube-controller-manager현재 상태가 선언한 상태와 같아지도록 Controller를 실행한다.
Worker NodekubeletNode에서 Pod와 컨테이너가 실행되도록 관리한다.
Worker NodeContainer Runtime컨테이너를 생성하고 실행한다.
Worker Nodekube-proxyService 트래픽을 Backend Pod로 전달하기 위한 네트워크 규칙을 관리한다.

Pod가 만들어질 때

  1. 사용자가 Pod 생성을 요청하면 API Server가 요청을 받는다.
  2. Scheduler가 Pod를 실행할 Node를 정한다.
  3. 선택된 Node의 kubelet이 Container Runtime에 Pod 실행을 요청한다.
  4. Pod Sandbox와 Network Namespace가 준비되고, 네트워크 플러그인이 Interface와 IP, Route를 설정한다.
  5. 컨테이너가 실행된다.

Week 1에서는 전체 순서만 본다. kubelet, CRI, CNI가 실제로 호출되는 과정은 Week 2에서 다룬다.

2. Linux Network Namespace / veth / bridge

Network Namespace

Network Namespace는 Linux 네트워크 환경을 나누는 기능이다. Namespace마다 Network Interface, IP 주소, Routing Table, Neighbor Table, 방화벽 규칙, Port 공간을 따로 가질 수 있다.

일반적인 Kubernetes Pod에서는 같은 Pod 안의 컨테이너들이 하나의 Network Namespace를 공유한다. 그래서 같은 Pod의 컨테이너는 같은 IP를 사용하고 localhost로 통신할 수 있다. 반대로 다른 Pod의 localhost에는 접근할 수 없다.

veth pair

veth는 항상 두 개가 한 쌍으로 만들어진다. 한쪽으로 보낸 Frame은 반대쪽에서 들어온다. Pod 네트워크에서는 한쪽을 Pod의 Network Namespace에 넣고, 다른 쪽을 Host Network Namespace에 두는 방식이 자주 사용된다.

Pod Network Namespace          Host Network Namespace

eth0  <------ veth pair ------>  host-side veth

Linux Bridge

Linux Bridge는 여러 Interface를 연결하는 L2 장치다. 일반 스위치처럼 MAC Address를 학습하고, 목적지 MAC Address를 보고 Frame을 내보낼 Port를 선택한다.

Bridge가 관리하는 FDB는 대략 다음 정보를 가진다.

MAC Address (+ VLAN) → Bridge Port

질문 1. 같은 Pod의 두 컨테이너가 모두 0.0.0.0:8080을 사용하려고 하면 어떻게 될까?

두 컨테이너가 같은 Network Namespace와 Port 공간을 공유하므로 Port 충돌이 발생한다.

veth와 Linux Bridge는 Pod 네트워크를 설명하기 좋은 예시지만 모든 CNI가 이 구조를 쓰는 것은 아니다. 이번 주에는 Linux 기능을 이해하기 위한 기본 모델로만 사용한다.

3. TCP/IP Stack

애플리케이션이 만든 데이터는 TCP/IP Stack을 거치면서 네트워크로 전송할 수 있는 형태가 된다. 수신 측에서는 반대 순서로 Header를 확인하고 원래 데이터를 애플리케이션에 전달한다.

계층예이번 주에 볼 내용
ApplicationHTTP, DNS애플리케이션이 전송할 데이터를 만든다.
TransportTCP, UDPPort 번호를 사용해 Process를 구분한다.
InternetIPv4, IPv6Source/Destination IP를 사용하고 Route를 조회한다.
LinkEthernet같은 Link에서 MAC Address를 사용해 Frame을 전달한다.

Pod A에서 Pod B로 보낼 때

Application data
  → TCP/UDP segment
  → IP packet
  → Ethernet frame
  → Pod eth0
  → veth
  → Linux Bridge
  → veth
  → Pod B eth0
  → IP
  → TCP/UDP
  → Application

IP Packet 안의 목적지 IP와 Ethernet Frame의 목적지 MAC은 같은 역할이 아니다. IP는 최종 통신 대상을 나타내고, MAC은 현재 Link에서 Frame을 다음 장치로 전달할 때 사용한다.

질문 2. Packet이 Router를 통과해도 목적지 IP와 목적지 MAC이 계속 같을까?

목적지 IP는 일반적으로 최종 목적지를 유지한다. Ethernet Header는 Link가 바뀔 때마다 새로 만들어지므로 목적지 MAC도 next hop에 맞게 달라진다.

참고: RFC 1122 - Requirements for Internet Hosts

4. Routing / ARP

Routing

Routing은 목적지 IP를 보고 Packet을 어느 Interface로 내보낼지, next hop은 누구인지 정하는 과정이다. Linux는 Network Namespace마다 Routing Table을 가질 수 있다.

# 현재 Routing Table 확인
ip route

# 특정 목적지로 갈 때 선택되는 경로 확인
ip route get 10.244.0.3

ARP

ARP는 같은 Link에서 IPv4 주소에 해당하는 MAC Address를 찾는다. Neighbor Cache에 정보가 없으면 ARP Request를 Broadcast하고, 해당 IP를 가진 장치가 자신의 MAC Address로 응답한다.

ARP / Neighbor Table
IP Address → MAC Address

Bridge FDB
MAC Address (+ VLAN) → Bridge Port

같은 Subnet과 다른 Subnet

목적지Route 판단ARP로 찾는 MAC
같은 Subnet직접 연결된 Network목적지 장치의 MAC
다른 SubnetGateway 또는 next hop 사용Gateway/next hop의 MAC

동일 Node, 같은 L2 Bridge에 있는 두 Pod

  1. Pod A가 Pod B의 IP로 Packet을 만든다.
  2. Pod A의 Routing Table이 출력 Interface와 next hop을 정한다.
  3. Pod B의 MAC이 Neighbor Cache에 없으면 ARP Request를 보낸다.
  4. Broadcast Frame이 veth를 지나 Linux Bridge에 도착한다.
  5. Bridge는 Source MAC을 학습하고 ARP Request를 다른 Port로 전달한다.
  6. Pod B가 ARP Reply를 보내면 Pod A는 Pod B IP → Pod B MAC을 저장한다.
  7. 이후 Bridge는 FDB를 보고 Data Frame을 Pod B 쪽 veth로 전달한다.

이 예시는 같은 L2 Bridge Subnet을 전제로 한다. CNI가 Gateway 방식이나 L3 Routing을 사용하면 Pod가 최종 Pod의 MAC이 아니라 Gateway MAC을 조회할 수 있다.

5. Netfilter / iptables

Netfilter

Netfilter는 Linux Kernel의 Packet 처리 경로에 Hook을 제공하는 Framework다. Kernel Module이나 규칙은 이 Hook에서 Packet을 허용하거나 차단하고, 주소를 변환하거나 기록할 수 있다.

iptables

iptables는 Netfilter에 사용할 규칙을 설정하고 조회하는 사용자 공간 도구다. Netfilter와 iptables는 같은 말이 아니다.

수신 Packet
  → PREROUTING
  → Routing 판단
      ├─ Local 목적지 → INPUT → Local Process
      └─ 다른 Interface → FORWARD → POSTROUTING → 송신

Local Process가 만든 Packet
  → OUTPUT → POSTROUTING → 송신
항목하는 일
Routing TablePacket을 어디로 보낼지 정한다.
NetfilterPacket 처리 경로에서 규칙을 적용한다.
iptablesNetfilter 규칙을 설정하고 확인한다.

Bridge로 L2 Forwarding되는 Frame이 항상 IPv4 FORWARD Chain을 지나는 것은 아니다. br_netfilter 설정에 따라 Bridged Traffic이 IP Netfilter Hook의 영향을 받을 수 있다.

# iptables 규칙 확인
iptables-save

# nftables를 사용하는 환경
nft list ruleset

# Bridge Traffic의 iptables 처리 설정 확인
lsmod | grep br_netfilter
sysctl net.bridge.bridge-nf-call-iptables

질문 3. br_netfilter를 끄면 Linux Bridge 자체가 동작하지 않을까?

Bridge의 L2 Forwarding은 계속 동작한다. 달라지는 부분은 Bridged Traffic을 IP Netfilter Hook에서 처리하는 방식이다.
