1Multus Architecture / CNI Chaining

1.1멀티 네트워크가 필요한 이유

일반적인 Multus 구성에서는 기존 클러스터 네트워크를 유지하면서 Pod에 추가 인터페이스를 연결함. 기본 연결은 보통 eth0, 추가 연결은 net1, net2 같은 이름으로 나타남.

학습용 사용 사례는 다음과 같음.

  • 관리 통신은 기본 네트워크로 유지하고, 데이터 통신은 별도 망으로 연결하는 경우
  • Pod를 기존 외부 L2 네트워크에 연결해야 하는 경우
  • 지원 NIC의 하드웨어 기능을 Pod에 할당해야 하는 경우

여기서 비교 대상은 ‘하나의 실행 환경이 여러 연결을 가진다’는 구조임. Pod를 VM과 동일하게 보거나, 추가 인터페이스마다 반드시 별도 물리 NIC가 필요하다고 해석하는 것은 아님.

1.2Multus는 연결을 구성하는 메타 CNI임

Multus는 다른 CNI 플러그인을 호출해 Pod에 여러 네트워크 인터페이스를 연결하는 메타 CNI 플러그인임. 실제 연결 방식은 호출되는 기본 CNI와 추가 CNI가 담당함.

이 그림은 설정 책임을 보여주는 개념도임. 배포 형태에 따라 Multus 내부 호출 구조는 달라질 수 있음. 중요한 것은 Multus가 연결 구성을 조정한다는 점과, 모든 패킷이 Multus 프로세스를 거쳐 전달되는 것은 아니라는 점임.

기존 인프라 업무로 대응시키면, Multus는 ‘어떤 네트워크를 연결할지 정하고 필요한 작업자를 호출하는 조정자’에 가까움. 스위치·라우터처럼 모든 데이터 패킷을 중계하는 장비로 이해하면 안 됨.

Multus와 가장 닮은 개념도로 아래 Red Hat 블로그 “Demystifying Multus”의 그림을 함께 볼 수 있음. Kubernetes가 메타 플러그인(Multus)을 호출하고, Multus가 CRD에 저장된 설정을 참고해 기본 CNI와 추가 CNI를 각각 호출하며, 그 결과로 Pod에 eth0와 추가 인터페이스가 생기는 구조임. 위 개념도와 같은 관계를 다른 표현으로 그린 그림임.

1.3CNI Chaining은 여러 플러그인의 순차 실행임

CNI Chaining은 하나의 네트워크 설정 목록에서 여러 플러그인을 순서대로 실행하고, 앞 단계의 결과를 prevResult로 다음 단계에 전달하는 방식임. 예를 들어 연결 생성 후 인터페이스 설정이나 포트 매핑을 보완할 수 있음.

구분CNI ChainingMulti-Networking
핵심여러 플러그인이 한 연결의 구성을 나누어 수행함Pod에 여러 네트워크 연결을 제공함
관찰 대상설정 목록과 플러그인 실행 순서Pod 인터페이스와 연결 대상
혼동 방지플러그인이 여러 개라고 NIC도 여러 개인 것은 아님추가 연결 안에서 Chaining을 함께 사용할 수도 있음

두 개념은 함께 사용할 수 있지만 같은 의미는 아님.

토론 질문 1. CNI 플러그인 세 개를 순서대로 실행했다면 Pod 인터페이스도 반드시 세 개가 되는가? 실행 단계와 연결 개수를 구분해서 설명할 필요가 있음.

2Primary / Secondary Network

2.1Primary는 기본 연결, Secondary는 추가 연결임

Multus의 일반적인 구성에서 Primary Network는 클러스터 기본 네트워크이고, Secondary Network는 별도 목적을 위한 추가 네트워크임. eth0와 net1은 대표적인 이름이며 추가 인터페이스명은 지정할 수도 있음.

구분Primary NetworkSecondary Network
역할기본 클러스터 연결별도 목적의 추가 연결
대표 인터페이스명eth0net1, net2 또는 지정 이름
구성 담당 예Flannel, Calico, Ciliummacvlan, ipvlan, SR-IOV

Primary/Secondary는 역할 구분임. 특정 플러그인이 어떤 경우에도 Primary 또는 Secondary로만 쓰인다는 고정 분류는 아님.

2.2인터페이스 추가와 기본 경로 변경은 별개임

추가 NIC가 생겼다는 것은 통신 출입구가 추가되었다는 뜻임. 모든 통신이 자동으로 그쪽으로 전환되는 것은 아님. Multus 문서에서는 일반적인 기본 경로가 eth0를 사용하며, 별도 attachment를 기본 경로로 지정할 수도 있음을 설명함.

기본 경로를 net1로 바꾸면 클러스터 네트워크로 향하던 통신에도 영향을 줄 수 있음. NIC 이름이 아니라 목적지별 라우팅 결과로 실제 출구를 확인해야 함.

2.3추가 연결이 보안 분리를 보장하지는 않음

이 노트의 운영 검토 항목은 다음과 같음. 아래는 실제 환경에서 확인한 결과가 아니라, 도입 시 별도로 검증해야 할 조건임.

  • 기본 연결과 추가 연결이 실제로 서로 다른 VLAN·물리망·방화벽 경계를 사용하는지
  • 기본 CNI의 정책이 추가 연결에도 적용되는지, 별도 정책 수단이 필요한지
  • 추가 연결이 기존 접근통제 경계를 우회하지 않는지
  • 기본 경로 변경 후 Service·DNS·API 등 필요한 통신이 유지되는지
  • 추가 인터페이스의 IP를 기존 네트워크에서 어떤 방식으로 접근·통제할지

서버에 NIC 두 개를 달았다는 사실과 망 분리가 완료되었다는 판단을 구분하듯, Pod도 인터페이스·주소·경로·보안 정책을 나누어 확인해야 함.

3NetworkAttachmentDefinition

3.1NAD는 추가 네트워크의 연결 정의임

NetworkAttachmentDefinition, 줄여서 NAD는 추가 네트워크 설정을 Kubernetes 리소스로 정의한 것임. Multus가 이 정의를 읽고 필요한 CNI를 호출함.

  • CRD, CustomResourceDefinition: Kubernetes API에 새로운 리소스 종류를 등록하는 정의임.
  • NAD 객체: 등록된 종류를 사용해 작성한 실제 네트워크 연결 설정임.

기존 업무에 대응시키면 CRD는 ‘네트워크 연결 신청 양식의 종류’, NAD는 ‘그 양식으로 작성한 구체적인 연결 정의’에 가까움. 다만 NAD가 스위치 포트나 VLAN을 실제 외부 장비에 자동 생성한다는 뜻은 아님.

Pod에서는 k8s.v1.cni.cncf.io/networks annotation으로 사용할 NAD를 지정함. Annotation은 리소스에 추가 정보를 기록하는 메타데이터임.

3.2macvlan NAD 설정 예제

아래는 단일 노드 학습 환경을 가정한 NAD 객체 예제임. 실제 클러스터 적용이나 연결 확인은 수행하지 않았음. 192.0.2.0/24와 ens192는 설명용 값이며 운영 환경에 그대로 적용할 값이 아님.

NetworkAttachmentDefinition · YAML (설명용)
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: data-net
  namespace: default
spec:
  config: |
    {
      "cniVersion": "0.3.1",
      "name": "data-net",
      "type": "macvlan",
      "master": "ens192",
      "mode": "bridge",
      "ipam": {
        "type": "host-local",
        "ranges": [[{
          "subnet": "192.0.2.0/24",
          "rangeStart": "192.0.2.100",
          "rangeEnd": "192.0.2.120"
        }]]
      }
    }

이 설정을 읽는 순서는 다음과 같음.

  1. metadata.name: data-net: Pod가 참조할 NAD 이름임.
  2. spec.config: 해당 연결의 CNI 설정을 JSON 문자열로 담는 영역임.
  3. type: macvlan: 연결 구성에 사용할 CNI 플러그인임.
  4. master: ens192: 이 예제에서 사용할 Node 쪽 부모 인터페이스임. Pod의 eth0가 아님.
  5. mode: bridge: macvlan의 동작 모드임. 별도 bridge CNI 플러그인을 사용한다는 뜻이 아님.
  6. ipam.type: host-local: 호스트 로컬 상태를 이용하는 IP 주소 할당 방식임.
  7. ranges: 주소 할당 범위임. IP를 부여하는 설정과 외부 장비에서 돌아오는 경로 확보는 별개임.

cniVersion은 CNI 설정의 규격 버전임. Kubernetes 버전이나 Multus 제품 버전이 아님.

이 예제는 추가 연결에 기본 경로를 명시적으로 요청하지 않음. 다른 네트워크 대역에 접근하려면 목적지 경로·게이트웨이·응답 경로를 별도 설계해야 함.

3.3Pod에서 연결 요청하기

아래는 완전한 Pod manifest가 아니라 metadata 부분만 표시한 예제임. 컨테이너 이미지를 포함하는 spec은 생략함.

Pod metadata · YAML (일부)
metadata:
  name: multi-net-pod
  namespace: default
  annotations:
    k8s.v1.cni.cncf.io/networks: data-net

이 예제는 Pod와 같은 default namespace의 data-net NAD를 참조함. 다른 namespace의 NAD 참조나 인터페이스 이름 지정도 가능하지만, 이 노트에서는 동일 namespace의 기본 예제를 사용함.

NAD를 작성하는 것과 실행 중인 Pod의 NIC가 바뀌는 것은 같은 사건이 아님. 이 문서는 Pod 네트워크 설정 시 annotation을 참고해 연결하는 흐름을 다루며, 실행 중인 Pod에 대한 동적 NIC 추가·변경 절차는 다루지 않음.

3.4IPAM에서 주의할 점

host-local은 주소 할당 상태를 호스트 파일시스템에 저장하며, 같은 호스트의 해당 할당 관리 범위에서 주소 중복을 방지하는 방식임. 클러스터 전체에 대한 중앙 IP 관리가 아님.

따라서 여러 Node가 같은 L2 망을 사용할 때 동일 풀을 그대로 반복 적용하면 주소 중복 위험이 있음. 노드별 풀 분리 또는 클러스터 범위에서 주소를 조정하는 IPAM 설계가 필요함. 외부 DHCP·고정 IP 사용 장비와의 충돌도 별도 확인 대상임.

3.5실제 적용 전 확인할 조건

  • 기본 CNI와 Multus가 준비되어 있는지
  • NAD 종류를 사용할 수 있도록 CRD가 등록되어 있는지
  • 대상 Node에 필요한 추가 CNI 플러그인이 있는지
  • master에 지정한 인터페이스와 외부 네트워크가 준비되어 있는지
  • 주소 풀과 라우팅 설계가 해당 노드 수·외부망 조건에 맞는지

위 항목을 확인하지 않은 상태에서는 YAML이 문법상 맞다는 사실만으로 연결 성공을 판단할 수 없음.

4macvlan / ipvlan / SR-IOV

4.1macvlan: 인터페이스마다 별도 MAC 사용

macvlan은 부모 인터페이스를 공유하면서 각 가상 인터페이스가 별도의 MAC 주소를 갖게 하는 방식임. MAC 주소는 Ethernet에서 인터페이스를 구분하는 링크 계층 주소임.

별도 MAC을 가진 연결을 기존 L2 네트워크에 제공하는 구성을 이해할 때 유용함. 기존 DHCP와 연계할 수도 있지만, macvlan을 쓴다고 자동으로 DHCP를 사용하는 것은 아니며 IPAM 선택은 별개임.

외부 스위치와 가상화 네트워크가 한 포트에서 여러 MAC 주소를 허용하는지 확인해야 함. 또한 Linux macvlan의 부모 인터페이스와 컨테이너 간 직접 통신에는 제한이 있어, 호스트 통신이 필요하면 별도 경로를 검토해야 함.

4.2ipvlan: 부모 MAC 공유, IP 기준으로 구분

ipvlan은 가상 인터페이스들이 부모 인터페이스의 MAC 주소를 공유하고, IP 주소를 기준으로 패킷을 구분하는 방식임.

CNI ipvlan 플러그인은 l2, l3, l3s 모드를 지원함. L2 모드와 L3 모드는 패킷 처리 방식이 다르며, L3 모드에서는 인터페이스가 broadcast·multicast를 송수신하지 않음. 따라서 L3 모드를 기존 L2 망에 연결하는 그림과 동일하게 이해하면 안 됨.

부모 MAC을 공유하는 방식이 필요한 상황의 검토 대상이지만, 이것만으로 모든 가상화·클라우드 네트워크 제한이 해소되는 것은 아님. ipvlan 역시 가상 인터페이스에서 부모 인터페이스로 직접 통신할 수 없는 제한이 있으므로 호스트 통신 경로를 따로 확인해야 함.

4.3SR-IOV: NIC의 하드웨어 기능을 나누어 할당

SR-IOV는 지원 NIC의 기능을 PF와 VF로 나누어 활용하는 기술임.

  • PF, Physical Function: VF를 관리하는 물리 기능임.
  • VF, Virtual Function: 컨테이너에 별도로 할당할 수 있는 하드웨어 기능임.

Kubernetes에서의 역할은 다음과 같이 구분됨.

구성 요소역할
VF 사전 준비NIC·드라이버·운영 구성에서 VF를 사용할 수 있게 준비함
SR-IOV Device PluginKubernetes의 VF 자원 등록·할당에 관여함
Multus할당된 VF의 장치 정보를 전달하며 SR-IOV CNI를 호출함
SR-IOV CNI전달받은 VF의 네트워크 설정을 수행함

VF 생성 자체는 SR-IOV CNI의 역할이 아님. CNI만 설치했다고 하드웨어 자원과 스케줄링 조건까지 준비되는 것은 아님.

지원 NIC·VF·드라이버 및 배치 가능한 Node 조건을 함께 검토해야 함. SR-IOV와 DPDK는 같은 의미가 아니며, SR-IOV CNI 문서에도 커널 드라이버 구성과 DPDK 사용자 공간 드라이버 구성이 구분되어 있음.

4.4세 방식의 선택 관점

아래는 특성에 따른 학습용 선택 기준이며, 실제 성능 측정 결과나 특정 환경에 대한 도입 권고가 아님.

macvlan가상 인터페이스마다 별도 MAC별도 MAC을 가진 L2 연결이 필요함다중 MAC 허용, 호스트 통신 제한

이 선택에서 ‘어느 것이 무조건 더 빠른가’보다 필요한 연결 구조와 운영 제약이 무엇인가를 먼저 구분하는 것이 중요함.

5Multi-NIC Pod 구성 및 Packet Flow

5.1여러 인터페이스 중 출구는 어떻게 결정되는가

아래는 Linux Pod에서 기본 eth0와 macvlan net1을 사용하는 학습용 예제임. net1은 외부 L2 망에 연결된 Node 인터페이스를 부모로 사용한다고 가정함. 애플리케이션의 인터페이스 바인딩이나 별도 정책 라우팅이 없는 일반 IP 통신을 가정함.

이 예제에서는 목적지에 맞는 더 구체적인 경로를 우선 사용하며, 별도 일치 경로가 없으면 기본 경로를 사용함. 실제 판단은 ip route get으로 확인할 수 있음.

  • 192.0.2.50 목적지: 192.0.2.0/24에 해당하므로 net1 방향임.
  • 그 외 목적지: 더 구체적인 경로가 없다면 eth0의 기본 경로 방향임.
  • 목적지가 Service VIP인 경우: 인터페이스 선택만으로 Service 처리를 모두 설명할 수 없음. 실제 기본 CNI·Service 구현의 패킷 처리도 함께 확인해야 함.

5.2같은 L2 데이터망의 외부 장비로 보내는 흐름

아래는 목적지 192.0.2.50이 Pod와 같은 데이터망에 있고, macvlan bridge 모드로 통신하는 예제임.

이 과정에서는 역할을 나누어 이해해야 함.

  1. 라우팅: 목적지 IP를 보고 출구와 다음 홉을 선택함.
  2. 이웃 주소 확인: 이 예제의 같은 서브넷 IPv4 목적지에 대해 필요한 경우 ARP로 MAC을 확인함.
  3. 링크 전송: 선택된 인터페이스와 L2 망을 통해 프레임을 전달함.

다른 서브넷 목적지라면 설정된 경로와 게이트웨이를 사용해야 하며, ARP 대상도 보통 그 다음 홉이 됨. 주소 할당만으로 다른 망에 대한 라우팅이 자동 완성되는 것은 아님.

Multus는 이 연결을 구성하는 역할이며, 그림의 각 패킷을 중앙에서 중계하는 구성 요소로 넣지 않음. 이 흐름을 같은 Node 내부 통신, ipvlan L3 또는 SR-IOV/DPDK에 그대로 일반화하면 안 됨.

5.3응답 경로까지 확인해야 함

‘Pod에서 요청이 나갔다’와 ‘양방향 통신이 된다’는 다른 판단임. 다음은 이 예제에 대한 운영 점검 관점임.

  • 상대 장비가 Pod의 추가 IP로 응답할 수 있는지
  • 양쪽 서브넷·라우팅·게이트웨이 설정이 일치하는지
  • 외부 방화벽과 가상화 네트워크에서 요청·응답을 허용하는지
  • 같은 IP를 사용하는 다른 장비가 없는지

특히 NIC를 추가하거나 기본 경로를 바꾼 뒤에는 원래 기본 연결로 처리되던 통신도 함께 확인하는 것이 필요함.

5.4확인 명령과 읽는 순서

아래는 확인 명령 예시이며 실행 결과가 아님. 해당 Pod 이미지에 ip 도구가 있어야 하며, 접근 권한과 환경에 맞게 사용할 필요가 있음.

확인 명령 예시 · bash (실행 결과 아님)
# Kubernetes에서 Pod 배치와 상태 확인
kubectl get pod multi-net-pod -n default -o wide
kubectl describe pod multi-net-pod -n default

# NAD 정의 확인
kubectl get network-attachment-definitions -n default
kubectl get network-attachment-definition data-net -n default -o yaml

# Pod 내부 인터페이스와 IP 확인
kubectl exec -n default multi-net-pod -- ip -br addr

# Pod 내부 라우팅 확인
kubectl exec -n default multi-net-pod -- ip route

# 특정 목적지의 출구와 출발지 주소 확인
kubectl exec -n default multi-net-pod -- ip route get 192.0.2.50

# 필요한 경우 이웃 주소 상태 확인
kubectl exec -n default multi-net-pod -- ip neigh

Pod에 여러 컨테이너가 있으면 필요에 따라 kubectl exec의 -c 옵션으로 도구가 있는 컨테이너를 선택해야 함. 명령이 없다는 오류와 네트워크 장애를 혼동하지 않아야 함.

이 예제의 점검 순서는 다음과 같이 잡을 수 있음.

순서확인 질문확인 지점
1. 연결 요청원하는 NAD를 참조했는가?Pod annotation·NAD 이름·namespace
2. 연결 생성net1이 실제로 존재하는가?Pod 이벤트·Multus/CNI 설정·인터페이스
3. 주소기대한 IP·서브넷인가?IPAM·주소 풀·중복 가능성
4. 출구목적지로 어느 인터페이스를 쓰는가?ip route, ip route get
5. 외부·응답부모 NIC·외부망·복귀 경로가 맞는가?VLAN·스위치·방화벽·상대 경로

이는 실제 장애를 재현한 결과가 아니라, 앞서 설명한 구성 책임과 통신 경로를 분리해 확인하기 위한 학습용 체크리스트임.

5.5이번 주 내용의 연결

이번 주의 핵심은 ‘CNI를 여러 개 설치한다’가 아니라 다음의 역할 분리임.

  • Multus

    필요한 네트워크 연결을 위해 다른 CNI를 호출함.

  • NAD

    추가 연결의 설정을 정의함.

  • macvlan / ipvlan / SR-IOV CNI

    선택한 방식으로 연결을 구성함.

  • IPAM

    사용할 IP 주소를 할당함.

  • 라우팅과 실제 데이터 경로

    목적지에 맞는 출구와 패킷 전달을 결정함.

따라서 추가 NIC가 보이는지만 확인하지 않고, 연결 목적 → 주소 할당 → 경로 → 외부 연결 → 보안·응답 조건을 나누어 이해해야 함.

  1. 연결 목적
  2. 주소 할당
  3. 경로
  4. 외부 연결
  5. 보안·응답 조건
