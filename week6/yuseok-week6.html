클클 쿠버네크 6주차 정리본

Week 6. Multi-Networking & Secondary Networking

하나의 Pod에 여러 네트워크를 연결하는 방식과 Multus의 역할을 살펴본다. Primary / Secondary Network, NetworkAttachmentDefinition, macvlan / ipvlan / SR-IOV를 비교하고, 여러 인터페이스를 가진 Pod의 라우팅과 패킷 흐름을 정리한다.

1. 멀티 네트워크가 필요한 이유

일반적인 Pod는 기본 클러스터 네트워크를 통해 다른 Pod, Service, 외부 시스템과 통신한다. 하지만 워크로드에 따라 별도의 네트워크 연결이 필요할 수 있다.

예를 들어 애플리케이션 Pod가 eth0으로 클러스터 통신을 유지하면서, net1으로 스토리지 서버에 접근하도록 구성할 수 있다.

목적사용 사례
트래픽 분리관리 트래픽과 사용자 데이터 트래픽을 별도 네트워크로 전달
기존 네트워크 연동Pod를 기존 장비나 서버가 사용하는 L2 네트워크에 연결
고성능 패킷 처리SR-IOV와 DPDK 등을 활용하는 통신 워크로드
스토리지 통신 분리서비스 요청과 스토리지 복제·백업 트래픽을 별도 대역으로 전달
가상머신 워크로드Kubernetes에서 실행하는 VM에 여러 네트워크 연결 제공

추가 인터페이스가 있다고 해서 처리량 증가, QoS 보장, 보안 격리가 자동으로 이루어지는 것은 아니다. 같은 물리 NIC를 공유하면 대역폭과 장애 지점도 공유할 수 있으며, 보안 격리에는 VLAN·라우팅·접근 제어 등의 구성이 함께 필요하다.

SR-IOV와 DPDK의 차이

  • SR-IOV: NIC가 제공하는 여러 가상 기능인 VF를 워크로드에 할당하는 하드웨어 가상화 기술이다. 호스트의 소프트웨어 가상 스위치 경로를 우회하여 오버헤드를 줄일 수 있다.
  • DPDK: 사용자 공간에서 고속 패킷 처리를 수행하기 위한 라이브러리와 드라이버 모음이다. 지원되는 드라이버와 애플리케이션 구성을 통해 일반적인 커널 패킷 처리 경로를 우회할 수 있다.

SR-IOV 자체가 커널 우회를 의미하지는 않는다. VF를 일반적인 커널 네트워크 드라이버로 사용할 수도 있고, DPDK 사용자 공간 드라이버로 사용할 수도 있다. github.com

2. Primary / Secondary Network

구분Primary NetworkSecondary Network
의미Pod의 기본 클러스터 네트워크특정 목적을 위해 추가한 네트워크
인터페이스 예시eth0net1, net2 또는 지정한 이름
CNI 예시Calico, Cilium, Flannel 등macvlan, ipvlan, SR-IOV 등
주요 용도일반적인 Pod·Service 통신스토리지망, 기존 장비망, 고성능 데이터망
구성 방식기본 네트워크 설정으로 구성일반적인 Multus 구성에서는 Pod 어노테이션으로 선택

일반적인 단일 네트워크 Pod에서는 lo와 eth0을 볼 수 있다. Multus를 사용하면 같은 Pod의 네트워크 네임스페이스에 추가 인터페이스를 연결할 수 있다.

Secondary Network는 추가 네트워크라는 의미이며, 자동 장애 전환을 위한 백업 네트워크를 뜻하지 않는다.

또한 인터페이스 수와 IP 주소 수는 같은 개념이 아니다. 하나의 인터페이스에 여러 IP를 설정할 수 있으며, dual-stack Pod는 IPv4와 IPv6 주소를 함께 가질 수 있다.

3. Multus CNI

Multus는 Pod에 여러 네트워크 인터페이스를 연결하도록 다른 CNI 플러그인을 호출하는 메타 플러그인이다.

실제 인터페이스 구성은 Multus가 호출한 위임 플러그인(delegate plugin)이 수행한다.

예를 들어 기본 네트워크는 Calico로 구성하고, 추가 네트워크는 macvlan으로 구성할 수 있다.

이처럼 여러 네트워크에 연결된 Pod를 멀티홈 Pod(Multi-Homed Pod)라고 부른다.

Multus는 네트워크 구성 요청을 처리한다. 일반적인 통신에서 매 패킷을 Multus 데몬으로 보내 경로를 결정하는 구조는 아니다. 생성된 인터페이스와 라우팅 설정을 이용해 커널이나 해당 데이터 처리 방식이 패킷을 전달한다.

4. CNI Chaining과 Multus

CNI 설정의 plugins 목록을 이용하면 여러 플러그인을 순서대로 실행할 수 있다. 뒤의 플러그인은 앞선 플러그인의 실행 결과인 prevResult를 전달받는다.

대표적인 예시는 인터페이스를 생성한 뒤 portmap, bandwidth, sbr 등의 기능을 적용하는 것이다.

구분CNI ChainingMultus
중심 역할여러 플러그인을 순서대로 실행하며 네트워크 구성을 완성여러 네트워크 연결을 위해 CNI 플러그인에 위임
대표 사례인터페이스 생성 후 포트 매핑·대역폭 제한·라우팅 규칙 추가기본 eth0에 추가로 net1, net2 연결
설정CNI 설정의 plugins 목록기본 네트워크 설정, NAD, Pod 어노테이션
함께 사용 가능 여부Multus가 위임하는 네트워크 설정 안에서도 체인 사용 가능추가 네트워크에 CNI 체인 적용 가능

CNI Chaining과 Multus는 함께 사용할 수 있다. 예를 들어 추가 네트워크에서 ipvlan으로 인터페이스를 만든 뒤 SBR 플러그인으로 출발지 기반 라우팅을 설정할 수 있다.

CNI Chaining은 기존 인터페이스에 기능을 추가하는 것이 대표적인 사용 방식이지만, 사양상 인터페이스가 반드시 하나로 제한되는 것은 아니다. www.cni.dev

5. Multus Thick Plugin 구조

Thick Plugin은 Multus를 클라이언트와 서버로 나누어 배포하는 방식이다.

  • multus-shim: 컨테이너 런타임이 호출하는 CNI 바이너리다. 요청을 데몬에 전달하고 결과를 반환한다.
  • multus-daemon: 노드별로 실행되며, 네트워크 설정을 확인하고 위임 CNI 플러그인을 호출한다.
  • 유닉스 도메인 소켓: shim과 daemon 사이의 통신에 사용된다. 기본 소켓 디렉터리는 /run/multus다.
구성 요소일반적인 위치역할
multus-shim노드의 /opt/cni/bin런타임 요청과 데몬 결과 중계
00-multus.conf노드의 /etc/cni/net.d런타임이 Multus를 호출하도록 설정
Multus DaemonSetKubernetes 리소스노드별 Multus Pod 배포
multus-daemonDaemonSet이 배포한 Pod 내부설정 확인 및 위임 플러그인 실행
NADKubernetes API의 사용자 정의 리소스추가 네트워크 설정 제공
위임 CNI 플러그인일반적으로 노드의 /opt/cni/bin인터페이스와 네트워크 구성

파일 경로와 설정 선택 방식은 배포 환경과 런타임 설정에 따라 달라질 수 있다.

Pod 네트워크 생성 과정

  1. kubelet이 컨테이너 런타임에 Pod sandbox 생성을 요청한다.
  2. 런타임이 Pod 네트워크 네임스페이스를 준비하고 multus-shim을 호출한다.
  3. shim이 유닉스 도메인 소켓으로 daemon에 요청을 전달한다.
  4. daemon이 기본 네트워크 설정과 Pod의 추가 네트워크 요청을 확인한다.
  5. 기본 CNI와 추가 CNI를 호출하여 인터페이스를 구성한다.
  6. 연결 상태를 기록하고 결과를 런타임에 반환한다.

6. NetworkAttachmentDefinition과 Pod 어노테이션

  • NetworkAttachmentDefinition(NAD)은 추가 네트워크의 CNI 설정을 제공하는 네임스페이스 단위 사용자 정의 리소스다. 해당 리소스 유형은 CRD로 등록된다.
항목역할
NAD의 spec.config사용할 CNI 플러그인과 IPAM 등의 설정
Pod의 networks 어노테이션사용할 추가 네트워크 선택
Pod의 network-status 어노테이션연결된 인터페이스와 IP 등의 결과 확인

NAD 예시

다음은 노드의 eth1을 부모로 사용하는 macvlan 네트워크 정의 예시다.

apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: storage-net
  namespace: default
spec:
  config: |
    {
      "cniVersion": "0.3.1",
      "name": "storage-net",
      "type": "macvlan",
      "master": "eth1",
      "mode": "bridge",
      "ipam": {
        "type": "host-local",
        "ranges": [
          [
            {
              "subnet": "192.168.100.0/24",
              "rangeStart": "192.168.100.40",
              "rangeEnd": "192.168.100.60"
            }
          ]
        ]
      }
    }
필드의미
type사용할 CNI 플러그인
master노드 쪽 부모 인터페이스
modemacvlan 동작 모드
ipam.typeIP 주소 할당 플러그인
subnet추가 네트워크의 IP 대역
rangeStart, rangeEnd할당에 사용할 주소 범위

이 예시는 단일 노드 학습용 구성이다. 실제 적용 시 부모 인터페이스와 외부 네트워크가 준비되어 있어야 하고, 할당 범위가 기존 장비의 주소와 겹치지 않아야 한다.

host-local은 노드 단위로 주소 할당을 관리한다. 여러 노드에서 같은 범위를 사용하면 주소 중복이 발생할 수 있으므로, 다중 노드 환경에서는 노드별 범위를 나누거나 클러스터 단위 IPAM을 사용해야 한다.

Pod에서 추가 네트워크 선택

apiVersion: v1
kind: Pod
metadata:
  name: multi-network-pod
  namespace: default
  annotations:
    k8s.v1.cni.cncf.io/networks: |
      [{"name": "storage-net", "interface": "net1"}]
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]

Pod 생성 시 Multus가 storage-net을 찾아 위임 플러그인을 호출하고, Pod 내부에 net1을 구성한다.

NAD 생성만으로 기존 Pod에 인터페이스가 자동 추가되지는 않는다. 일반적인 구성에서는 Pod 생성 시 어노테이션을 통해 연결을 요청한다. k8snetworkplumbingwg.github.io

7. macvlan / ipvlan / SR-IOV 비교

항목macvlanipvlanSR-IOV
기본 방식부모 NIC 위에 서로 다른 MAC을 가진 가상 인터페이스 생성부모 NIC의 MAC을 공유하고 IP로 구분NIC가 제공하는 VF를 워크로드에 할당
특별한 하드웨어 요구SR-IOV 기능 불필요SR-IOV 기능 불필요SR-IOV 지원 NIC와 VF 구성 필요
적합한 사례기존 L2망의 독립된 장비처럼 Pod 연결여러 MAC 사용이 제한된 환경고성능 통신·패킷 처리
주요 고려 사항외부망의 여러 MAC 허용 여부와 동작 모드L2 / L3 / L3S 모드와 라우팅VF 자원 수, 드라이버, 장치 할당

SR-IOV 구성 요소

  • PF(Physical Function): VF의 설정과 관리를 담당하는 NIC의 물리 기능.
  • VF(Virtual Function): 워크로드에 할당할 수 있는 가상 PCI 기능.
  • SR-IOV Device Plugin: VF 자원을 Kubernetes에 등록하고 할당에 참여한다.
  • SR-IOV CNI: 할당된 VF의 네트워크 설정을 수행한다.
  • Multus: 할당된 장치 정보를 SR-IOV CNI에 전달하고 실행을 위임한다.

VF 생성과 노드의 하드웨어 준비는 SR-IOV CNI 실행 전에 이루어져야 한다. github.com

8. Multi-NIC Pod의 라우팅

인터페이스를 여러 개 연결하는 것과 트래픽이 어느 인터페이스로 나가는지는 별개의 문제다.

일반적인 커널 네트워킹에서는 라우팅 규칙과 라우팅 테이블을 통해 출력 인터페이스와 다음 홉을 선택한다. 인터페이스가 추가되었다고 패킷이 자동 분산되지는 않는다.

목적지 기반 라우팅

다음은 이해를 위한 예시다.

인터페이스IP 주소용도
eth010.244.1.10/24클러스터 네트워크
net1192.168.100.10/24스토리지 네트워크
10.244.1.0/24 dev eth0 src 10.244.1.10
10.244.0.0/16 via 10.244.1.1 dev eth0
192.168.100.0/24 dev net1 src 192.168.100.10
default via 10.244.1.1 dev eth0

목적지와 일치하는 경로 중 더 구체적인 경로를 선택한다. 해당 경로가 없다면 기본 경로를 사용한다.

목적지선택되는 경로인터페이스
10.244.1.2010.244.1.0/24eth0
10.244.2.2010.244.0.0/16eth0
192.168.100.20192.168.100.0/24net1
별도 경로가 없는 외부 IPdefaulteth0

이는 예시 구성이며, 실제 클러스터의 경로와 게이트웨이는 CNI에 따라 달라진다.

기본 경로 변경

Multus의 default-route 어노테이션으로 추가 네트워크를 기본 경로로 선택할 수 있다.

metadata:
  annotations:
    k8s.v1.cni.cncf.io/networks: |
      [{
        "name": "macvlan-conf",
        "default-route": ["192.168.2.1"]
      }]

공식 문서의 결과 예시는 다음과 같다.

default via 192.168.2.1 dev net1
10.244.0.0/24 dev eth0
10.244.0.0/16 via 10.244.0.1 dev eth0

클러스터 대역으로 가는 명시적인 경로는 여전히 eth0을 사용한다. 그 밖에 더 구체적인 경로가 없는 목적지는 net1의 기본 게이트웨이를 사용한다.

따라서 Primary Network와 기본 경로는 같은 개념이 아니다. 기본 경로를 변경할 때 필요한 클러스터 경로가 유지되는지 확인해야 한다. k8snetworkplumbingwg.github.io

9. SBR: 출발지 기반 라우팅

목적지 IP만으로 트래픽의 용도를 구별하기 어려우면 Source Based Routing(SBR)을 사용할 수 있다.

예를 들어 관리망과 SIP 전화 통신망을 함께 사용하는 애플리케이션에서는 같은 외부 대역으로 통신하더라도 용도에 따라 다른 네트워크를 선택해야 할 수 있다.

이때 애플리케이션이 사용할 인터페이스의 IP를 출발지로 선택하고, 해당 출발지 IP에 맞는 라우팅 테이블을 사용하도록 규칙을 구성한다.

# 지정된 출발지 IP는 table 100을 조회
ip rule add from 192.168.1.209/32 table 100

# 해당 네트워크의 직접 연결 경로
ip route add 192.168.1.0/24 dev net1 table 100

# table 100의 기본 경로
ip route add default via 192.168.1.1 dev net1 table 100

처리 순서는 다음과 같다.

  1. 애플리케이션이 소켓을 특정 출발지 IP에 바인딩한다.
  2. Linux가 ip rule에 따라 라우팅 테이블을 선택한다.
  3. 선택된 테이블에서 목적지에 맞는 경로를 조회한다.
  4. 해당 경로의 인터페이스와 다음 홉으로 전송한다.

SBR은 패킷 내용을 분석해 트래픽 종류를 자동 분류하지 않는다. 이 사례에서는 애플리케이션의 출발지 선택과 라우팅 규칙이 함께 동작한다.

CNI의 SBR 플러그인은 인터페이스 생성 플러그인 뒤에 연결되어 이러한 규칙과 테이블 구성을 수행한다. www.cni.dev

10. ipvlan의 Packet Flow

ipvlan 인터페이스는 부모 NIC의 MAC을 공유하고, IP 주소를 기준으로 패킷을 구분한다. 실제 처리 경로는 동작 모드에 따라 달라진다.

아래는 커널 문서의 설명을 Pod와 노드의 네트워크 네임스페이스에 대응해 정리한 것이다.

모드송신 처리 흐름특징
L2Pod 쪽 스택에서 처리 → ipvlan 인터페이스 → 부모 NIC를 통해 송신브로드캐스트·멀티캐스트 송수신 가능
L3Pod 쪽에서 L3까지 처리 → 부모 쪽 스택으로 전달 → 부모 쪽 라우팅과 L2 처리 → 출력 NIC자식 인터페이스의 브로드캐스트·멀티캐스트 송수신 불가
L3SL3와 유사한 흐름에 conntrack 지원을 위한 처리 추가연결 추적이 필요한 경우 사용

수신 시에는 목적지 IP를 기준으로 해당 ipvlan 인터페이스를 구분하여 연결된 네임스페이스로 전달한다. L3 모드에서는 자식 인터페이스에 브로드캐스트·멀티캐스트 트래픽을 전달하지 않는다.

ipvlan L3는 Pod 내부의 경로만 확인해서 전체 흐름을 설명하기 어렵다. 부모 쪽 네트워크 스택의 라우팅도 함께 확인해야 한다. docs.kernel.org

11. AWS EKS의 활용 사례

AWS가 공식 지원하는 Multus 구성에서는 Amazon VPC CNI를 primary CNI로 사용한다. 추가 네트워크에는 ipvlan이나 host-device 등을 활용할 수 있다.

방식연결 구조고려 사항
VPC CNI + ipvlan기본 네트워크 유지, 추가 ENI를 부모로 ipvlan 인터페이스 구성하나의 부모 인터페이스를 여러 Pod가 공유 가능
VPC CNI + host-device기본 네트워크 유지, 별도 장치를 Pod에 제공장치의 독점 사용과 드라이버 구성 고려

일반적인 커널 인터페이스를 사용하는 host-device 구성에서는 호스트 인터페이스를 Pod 네임스페이스로 이동한다. DPDK용 장치는 드라이버와 장치 접근 방식이 다르며, 일반적인 net1 커널 인터페이스로 보이지 않을 수 있다.

host-device 자체가 DPDK나 커널 우회를 의미하지 않는다. 장치와 드라이버, 애플리케이션 구성이 함께 준비되어야 한다. docs.aws.amazon.com
