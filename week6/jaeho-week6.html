01 · Multus

Multus 는 CNI 자리에 들어가 문을 더 내는 플러그인입니다.

Multus 는 인터페이스를 직접 만들지 않는다. 앞문은 Calico 에, 뒷문은 macvlan 에 시키는 중개자다. 지난 주에 본 Calico 동작은 그대로다
01 · CNI Chaining 과 다른 점

체이닝은 한 문에 장치를 덧다는 것, 위임은 문을 더 내는 것

체이닝은 인터페이스 하나에 기능을 더하는 CNI 표준 기능이다. 인터페이스를 더 만드는 것은 Multus 의 위임이고, 둘은 별개다

03 · NetworkAttachmentDefinition

NAD 는 뒷문의 설계도입니다.

# macvlan-conf.yaml — Multus 가 읽는 CRD

apiVersion: "k8s.cni.cncf.io/v1"

kind: NetworkAttachmentDefinition

metadata:

name: macvlan-conf

namespace: storage

spec:

config: '{

"cniVersion": "0.3.1",

"type": "macvlan",

"master": "eth1",

"mode": "bridge",

"ipam": {

"type": "whereabouts",

"range": "192.168.100.0/24",

"gateway": "192.168.100.1"

}

}'

1이름 = Pod 가 부르는 호출명

Pod 는 annotation 에 이 이름을 적어 뒷문을 요청한다. 이름만 적으면 같은 namespace 에서 찾고, 다른 곳은 ns/이름 으로 적는다

2type = 어떤 방법으로 문을 낼까

macvlan · ipvlan · sriov 등 CNI 플러그인 이름. 이 값에 따라 아래 설정 항목도 달라진다

3master = 어느 NIC 을 나눠 쓸까

노드의 물리 NIC 이름. 이 NIC 이 꽂힌 VLAN 이 net1 의 네트워크가 된다. 모든 노드에서 같은 이름이어야 한다

4ipam = 누가 IP 를 줄까

whereabouts 는 클러스터 전체에서 겹치지 않게 준다. host-local 은 노드 단위라 같은 대역을 쓰면 노드끼리 겹친다

NAD 를 만들어도 인터페이스는 아직 생기지 않는다. Pod 가 annotation 에 이 이름을 적을 때 비로소 만들어진다

04 · 세 가지 방법

NIC 하나를 Pod 여럿이 나눠 쓰는 세 가지 방법

차이는 두 가지다. 스위치에 MAC 이 몇 개로 보이는지, 쪼개는 주체가 커널인지 NIC 인지. 이 둘이 어떤 환경에 맞는지를 결정한다
04 · SR-IOV

SR-IOV 만 다른 점 — NIC 이 직접 쪼갭니다.

호스트 네트워크 스택을 거치지 않아 가장 빠르다. 지원 NIC · device plugin · BIOS 설정이 필요하고 VF 개수에 한계가 있다

05 · Packet Flow

같은 Pod 에서 나간 패킷, 앞문과 뒷문의 길 비교

net1 이 빠른 이유는 거치는 단계가 적기 때문이다. 호스트에서 패킷을 보려면 tcpdump 를 eth1 에서 뜨고, 접근 제어는 스위치 ACL 로 한다
05 · 운영

뒷문을 낸 뒤 자주 넘어지는 세 곳

셋 다 net1 도 쿠버네티스가 관리해 줄 것이라는 기대에서 생긴다. 쿠버네티스는 인터페이스를 만들어 줄 뿐이고, 정책 · IP · 경로는 NAD 와 물리망 설정의 몫이다
06 · 선택

선택을 가르는 세 가지 기준

물리 서버면 macvlan, 클라우드 VM 이면 ipvlan, 지연이 중요한 워크로드면 SR-IOV. 한 클러스터에 NAD 를 여러 개 두고 섞어 써도 된다
