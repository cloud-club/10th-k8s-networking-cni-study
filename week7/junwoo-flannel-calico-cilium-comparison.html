Kubernetes 네트워킹

CNI 플러그인 비교

Pod의 패킷이 다른 노드의 Pod에 도착하기까지 Flannel, Calico, Cilium이 각각 무엇을 하는지 정리한다.

핵심 특징 각 2장, 동작 원리 각 2장(패킷 경로 애니메이션 포함), 비교 요약 1장

Flannel

노드마다 서브넷을 나누고 VXLAN 터널로 연결하는 단순한 오버레이

Calico

BGP 라우팅으로 Pod IP를 전달하고 정책을 노드에서 집행

Cilium

eBPF로 전달, 정책, 로드밸런싱을 커널에서 처리

Flannel핵심 특징 1/2

Pod 간 연결만 제공하는 가장 단순한 CNI

노드마다 Pod 대역을 나누고, 노드 사이는 터널로 연결한다.

연결만 담당한다

Pod에 IP를 주고 노드 간 통신을 이어 주는 것까지만 한다. 네트워크 정책과 로드밸런싱은 제공하지 않는다.

노드마다 /24 서브넷

클러스터 Pod CIDR(예: 10.244.0.0/16)을 노드마다 /24로 나눈다. 같은 노드의 Pod는 같은 서브넷의 IP를 받는다.

구성이 가볍다

노드마다 flanneld가 DaemonSet으로 하나씩 실행된다. Kubernetes API의 Node 정보를 읽어 동작하므로 별도 저장소가 필요 없다.

하부 네트워크에 의존하지 않는다

기본 백엔드인 VXLAN은 노드 간 IP 통신만 되면 동작한다. 스위치나 라우터 설정을 바꾸지 않아도 된다.

Flannel핵심 특징 2/2

백엔드를 고르고, 정책은 따로 보완한다

노드 간 전달 방식은 백엔드로 정하며, 보안 기능은 포함되어 있지 않다.

백엔드전달 방식특징
VXLAN (기본)UDP 8472로 캡슐화노드 간 IP 연결만 필요하다
host-gw캡슐화 없이 라우팅노드가 같은 L2 서브넷에 있어야 하며 오버헤드가 가장 작다
WireGuard암호화 터널노드 간 트래픽을 암호화한다
UDP사용자 공간 터널성능이 낮아 디버깅용으로만 쓴다

한계와 보완

  • NetworkPolicy 미지원정책이 필요하면 Calico와 함께 쓰는 Canal 구성이나 다른 CNI를 선택한다.
  • 부가 기능 없음로드밸런싱, 가시성, L7 기능은 제공하지 않는다.
  • 적합한 경우소규모 클러스터와 학습, 테스트 환경처럼 요구사항이 단순할 때 쓴다.
Calico핵심 특징 1/2

Pod IP를 라우팅으로 전달하는 L3 네트워크

BGP 모드에서는 패킷을 캡슐화하지 않고 경로만 교환한다.

순수 L3 라우팅

각 Pod IP를 노드의 라우팅 테이블에 경로로 등록한다. BGP 모드에서는 패킷을 감싸지 않고 원본 그대로 전달한다.

BGP로 경로 교환

노드의 BIRD가 Pod IP 블록을 BGP로 광고한다. 물리 라우터와 피어링하면 Pod IP를 클러스터 밖에서도 라우팅할 수 있다.

블록 단위 IP 할당

노드에 IP 블록(IPv4 기본 /26)을 할당하고 모자라면 블록을 추가한다. 경로가 Pod 단위가 아닌 블록 단위로 집약된다.

구성 요소 세 가지

Felix는 노드에 경로와 정책 규칙을 설치하고, BIRD는 BGP 경로를 교환한다. Typha는 대규모 클러스터에서 API 서버 부하를 줄인다.

Calico핵심 특징 2/2

풍부한 정책과 선택 가능한 전달 모드

환경에 맞게 캡슐화 여부를 고르고, 정책은 노드에서 집행한다.

모드전달 방식조건
BGP 라우팅캡슐화 없음하부 네트워크가 Pod 경로를 전달해야 한다 (같은 L2 또는 BGP 피어링)
IP-in-IPIP 헤더로 한 번 더 감쌈노드 간 IP 연결만 있으면 된다
VXLANUDP로 캡슐화BGP를 쓸 수 없는 환경에서 사용한다
CrossSubnet서브넷 경계에서만 캡슐화IP-in-IP, VXLAN과 함께 쓰는 옵션이다

정책과 보안

  • NetworkPolicyKubernetes 표준 정책과 Calico 전용 정책을 쓴다. 허용과 거부 규칙, 우선순위, 클러스터 전역 적용을 지원한다.
  • 데이터플레인 선택iptables(기본), nftables, eBPF 중에서 고른다.
  • 암호화WireGuard로 노드 간 트래픽을 암호화한다.
Cilium핵심 특징 1/2

eBPF로 네트워킹과 보안을 커널에서 처리

iptables 규칙 체인 대신 eBPF 프로그램과 맵을 사용한다.

eBPF 데이터플레인

패킷 처리를 커널 안의 eBPF 프로그램이 수행한다. 규칙을 순서대로 검사하지 않고 해시 맵을 조회하므로 규칙이 늘어도 처리 시간이 크게 늘지 않는다.

kube-proxy 대체

Service 로드밸런싱을 eBPF 맵으로 처리한다. iptables 규칙 수 증가와 규칙 갱신 지연 문제가 없다.

identity 기반 보안

레이블이 같은 Pod 그룹에 숫자 identity를 부여하고 정책을 identity 기준으로 적용한다. Pod IP가 바뀌어도 정책은 유지된다.

전달 모드 선택

터널(VXLAN 또는 Geneve)과 네이티브 라우팅 중에서 고른다. 네이티브 라우팅은 캡슐화 없이 하부 네트워크의 라우팅을 이용한다.

Cilium핵심 특징 2/2

L7 정책, 가시성, 암호화를 기본 제공

별도 도구 없이 정책, 관찰, 암호화, 멀티 클러스터를 한 에이전트로 처리한다.

L7 네트워크 정책

HTTP 메서드와 경로, gRPC, Kafka, DNS 이름(FQDN) 기준으로 허용 규칙을 작성한다. L3, L4 정책도 함께 쓴다.

Hubble 가시성

흐름마다 출발지, 목적지, 허용 또는 차단 판정을 기록한다. 서비스 간 의존 관계를 확인할 수 있다.

투명한 암호화

WireGuard 또는 IPsec으로 노드 간 트래픽을 암호화한다. 애플리케이션을 수정할 필요가 없다.

확장 기능

ClusterMesh로 여러 클러스터를 연결한다. Gateway API, 사이드카 없는 서비스 메시, 대역폭 관리도 제공한다.

요구사항: eBPF 기능을 쓰므로 비교적 최신 리눅스 커널이 필요하다.

Flannel동작 원리 1/2

터널 전달에 필요한 항목을 미리 채운다

패킷이 지나갈 때는 이미 등록된 라우팅, ARP, FDB 항목만 조회한다.

  1. 서브넷 확인flanneld가 시작되면 Node 오브젝트에 할당된 podCIDR(예: 10.244.1.0/24)을 읽는다.
  2. VXLAN 장치 생성flannel.1을 만들고 자신의 MAC과 노드 IP를 Node 어노테이션에 게시한다.
  3. 다른 노드 감시새 노드가 보이면 그 노드의 서브넷, MAC, 노드 IP를 읽어 오른쪽 세 항목을 추가한다.
  4. Pod 연결Pod가 생기면 CNI가 veth 쌍을 만들어 한쪽을 cni0 브리지에 연결하고 노드 서브넷에서 IP를 할당한다.

Node 1에 추가되는 항목 (Node 2 정보 기준)

라우팅 · ip route10.244.2.0/24 via 10.244.2.0 dev flannel.1 onlink어느 장치로 보낼지 결정한다
ARP · ip neigh show dev flannel.110.244.2.0 lladdr aa:bb:cc:00:00:02 PERMANENT내부 프레임의 목적지 MAC을 결정한다
FDB · bridge fdb show dev flannel.1aa:bb:cc:00:00:02 dst 192.168.0.12외부 헤더의 목적지 노드 IP를 결정한다
Flannel동작 원리 2/2

Pod A에서 Pod B로 가는 패킷 경로

Node 1의 Pod A가 Node 2의 Pod B로 보낸다. VXLAN 백엔드 기준이다.

Calico동작 원리 1/2

Felix와 BIRD가 경로와 규칙을 설치한다

Pod는 브리지 없이 veth로 호스트 라우팅 테이블에 직접 연결된다.

  1. Pod 연결CNI가 veth 쌍을 만든다. 호스트 쪽 이름은 cali로 시작하며 브리지에 연결하지 않는다.
  2. Pod 내부 설정기본 경로를 169.254.1.1로 지정한다. 실제 장치가 아니며 호스트 veth가 proxy ARP로 응답한다.
  3. FelixPod IP마다 /32 경로를 설치하고, 정책을 iptables 규칙(ipset 포함)으로 변환한다.
  4. BIRD자기 노드의 IP 블록을 BGP로 광고하고, 다른 노드에서 받은 블록을 경로로 설치한다.

설정 예

Pod 안 · ip routedefault via 169.254.1.1 dev eth0모든 외부 트래픽이 호스트 veth로 향한다
Node 1 · 로컬 Pod 경로 (Felix)10.244.1.5 dev cali1a2b3c scope linkPod마다 /32 경로가 설치된다
Node 1 · 원격 블록 경로 (BIRD)10.244.2.64/26 via 192.168.0.12 dev eth0 proto birdBGP로 받은 Node 2의 Pod 블록이다
Calico동작 원리 2/2

Pod A에서 Pod B로 가는 패킷 경로

BGP 모드(캡슐화 없음)와 iptables 데이터플레인 기준이다.

Cilium동작 원리 1/2

에이전트가 eBPF 프로그램과 맵을 관리한다

패킷 경로의 각 지점에 eBPF 프로그램을 붙이고, 판단에 쓰는 데이터는 맵에 둔다.

  1. 변경 감시cilium-agent가 Kubernetes API에서 Pod, Service, 정책 변경을 감시한다.
  2. Pod 연결CNI가 veth 쌍을 만들고 호스트 쪽 lxc 인터페이스에 bpf_lxc를 붙인다. Pod마다 identity가 정해진다.
  3. 맵 갱신에이전트가 ipcache, policy, lb 맵을 채운다. ct 맵은 데이터플레인이 연결을 추적하며 갱신한다.
  4. 부착 지점노드 NIC에는 bpf_host, 터널 장치 cilium_vxlan에는 bpf_overlay가 붙는다.
맵키 → 값용도
ipcachePod IP → identity, 노드 IP목적지 identity와 터널 목적지 조회
policyidentity → 허용 여부정책 판정
lbService IP:포트 → 백엔드Service 로드밸런싱
ct연결 정보 → 상태연결 추적, 응답 패킷 허용
Cilium동작 원리 2/2

Pod A에서 Pod B로 가는 패킷 경로

터널(VXLAN) 모드 기준이다. 네이티브 라우팅이면 캡슐화 단계가 없다.
