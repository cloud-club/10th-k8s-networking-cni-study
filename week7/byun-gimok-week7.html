1eBPF 동작 원리

1.1Program / Verifier / JIT / Hook 구분

eBPF는 Linux 커널의 정해진 실행 지점에서 검증된 프로그램을 실행할 수 있게 하는 기술임. 네트워크뿐 아니라 추적·관찰 등에도 활용되지만, 이번 주에는 Cilium의 네트워크 처리에 초점을 둠.

용어뜻혼동하기 쉬운 점
Program실제로 실행할 처리 코드임정책 데이터가 바뀔 때마다 반드시 새 코드를 만들어야 하는 것은 아님
Verifier커널이 프로그램의 메모리 접근·인자 등 안전 조건을 검사하는 장치임방화벽 정책이 업무 의도에 맞는지 검사하는 것은 아님
JITBPF 명령을 해당 CPU의 기계어로 변환하는 기능임패킷이 올 때마다 소스코드를 다시 컴파일하는 것은 아님
Hook프로그램을 연결해 실행시키는 지점임모든 프로그램이 모든 Hook에서 실행되는 것은 아님

기존 인프라로 대응시키면 Program은 처리 로직, Map은 로직이 참고하는 테이블, Hook은 그 로직이 호출되는 위치임. Verifier와 JIT는 로직을 커널에 적재하고 실행하는 준비 과정에 해당함.

1.2커널에 적재되고 실행되기까지

아래는 일반적인 eBPF 프로그램의 생명주기를 단순화한 개념도임. Cilium의 특정 버전에서 빌드·적재 명령이 반드시 이대로 한 번씩 실행된다는 의미는 아님.

사용자 공간은 cilium-agent 같은 관리 프로그램이 실행되는 영역이고, 커널 공간은 운영체제가 네트워크·메모리 등을 관리하는 영역임. BPF 프로그램의 적재·Map 생성·관리에는 bpf() 시스템 호출이 사용됨.

중요한 구분은 관리 프로그램이 상태를 준비하는 과정과, 커널의 Program이 패킷을 처리하는 과정이 다르다는 점임. 일반적인 L3/L4 eBPF 처리에서 매 패킷을 cilium-agent에 보내 판단받는 구조로 이해하면 안 됨. 다만 L7 처리를 위해 사용자 공간 프록시를 사용하는 경로까지 없다는 뜻은 아님.

1.3Verifier가 확인하는 것

Verifier는 프로그램의 상태를 분석하며, 예를 들어 다음을 확인함.

  • 초기화되지 않은 레지스터나 스택 값을 읽는지
  • 허용된 메모리 범위 밖에 접근하는지
  • 패킷 헤더를 읽기 전에 필요한 길이 검사를 했는지
  • Map 조회 결과가 없을 수 있는데도 유효한 값처럼 접근하는지
  • 호출하는 커널 보조 함수에 올바른 형태의 인자를 전달하는지

Verifier는 커널에서 실행해도 되는 프로그램인지 검사하는 수단임. ‘허용해야 할 고객 통신을 차단했다’ 같은 업무 정책 오류나 전체 애플리케이션의 정상 동작까지 보장하는 장치는 아님.

1.4JIT와 Hook은 서로 다른 역할임

JIT는 명령의 실행 형태를 바꾸는 기능이고, Hook은 실행 시점을 정하는 연결 지점임. JIT 사용 여부는 커널·CPU 아키텍처·설정에 좌우됨. 모든 환경을 동일한 실행 방식으로 가정하지 않아야 함.

네트워크와 관련해 알아둘 지점은 다음과 같음.

실행 지점이해할 위치·시점주의할 점
XDPnative XDP 기준, 드라이버 수신의 이른 단계Cilium의 모든 패킷이 XDP를 거치는 것은 아님
tc인터페이스의 ingress/egress 패킷 처리 지점ingress/egress는 관찰하는 인터페이스 기준임
소켓 관련 cgroup Hook연결 요청 등 소켓 동작과 관련된 지점socket LB에서는 하위 패킷 처리 전에 백엔드가 선택될 수 있음

예를 들어 Pod가 밖으로 보낸 패킷은 Node 쪽 veth에서는 ingress로 관찰될 수 있음. ‘ingress이므로 항상 Pod로 들어가는 트래픽’이라고 단정하지 않아야 함. 문맥이 Pod 정책 방향인지 인터페이스 처리 방향인지 먼저 구분해야 함.

또한 XDP → tc → 소켓 Hook을 모든 패킷이 순서대로 통과하는 고정 경로로 그리면 안 됨. 소켓의 연결 동작과 NIC 수신은 서로 다른 진입 상황임. 실제 경로는 기능·설정·통신 방향에 따라 달라짐.

1.5선택 실습: 적재된 Program 확인

아래는 권한을 가진 Linux 테스트 Node에서 실행하는 조회 명령 예시임. 현재 Windows PC에서 실행한 결과가 아니며, bpftool 설치와 커널 접근 권한이 필요함.

bpftool 조회 · bash (예시, 실행 결과 아님)
# 적재된 BPF 프로그램 조회
sudo bpftool prog show

# 네트워크 관련 연결 지점 조회
sudo bpftool net

관찰할 내용은 Program의 ID·이름·종류와 네트워크 연결 지점임. bpftool net만으로 모든 종류의 BPF 연결을 확인했다고 판단하면 안 됨. 출력은 조회 범위와 커널·도구 버전에 따라 달라질 수 있음.

2BPF Map & Cilium Datapath

2.1Program과 Map을 나누는 이유

BPF Map은 커널에 유지되는 데이터 구조이며, Program이 실행 사이에도 상태를 보관하거나 다른 Program·사용자 공간과 공유하는 데 사용됨. Hash·Array·LPM Trie 등 여러 종류가 있으므로 모두 같은 형태의 테이블은 아님.

예를 들어 Service의 백엔드가 바뀌었다면, 처리 로직이 참조하는 Map 정보를 바꾸는 방식으로 새 상태를 반영할 수 있음. 모든 상태 변경이 Program 교체를 요구하는 것은 아님. 반대로 기능·설정 변경 등에 따라 Program 재적재가 필요한 경우까지 없다는 뜻은 아님.

Map을 모두 cilium-agent만 쓰는 읽기 전용 표로 이해하는 것도 부정확함. 연결 추적·카운터 등은 데이터 경로에서 갱신될 수 있으며, 접근 권한과 갱신 주체는 Map의 용도에 따라 다름.

2.2ipcache: IP와 Security Identity를 연결함

Cilium의 ipcache는 IP 또는 prefix에 대응하는 Security Identity 등 원격 endpoint 정보를 담는 Map임. 구성에 따라 터널 endpoint 같은 전달 관련 정보도 포함함. 실제 자료 구조와 필드는 버전에 따라 확인해야 함.

Security Identity는 정책 판단을 위해 쓰는 식별자이며, workload의 보안 관련 label 집합을 바탕으로 만들어짐. 예약된 Identity 등도 있어 모든 Identity를 개별 Pod 번호로 이해하면 안 됨.

기존 IP 기반 방화벽에서는 주소를 보고 대상을 판단하는 경우가 많음. Cilium은 label 기반의 보안 식별 정보를 데이터 경로에서 사용할 수 있게 연결함. 같은 보안 label 집합을 가진 workload는 Identity를 공유할 수 있으므로, Pod 하나와 Identity 하나가 항상 일대일 대응하는 것은 아님.

구분할 개념은 다음과 같음.

개념역할
IPAM사용할 IP를 할당하는 역할임
ipcacheIP·prefix와 Identity 등 데이터 경로 정보를 연결하는 역할임
Endpoint ID특정 Cilium endpoint를 식별하는 로컬 식별자임
Security Identity정책 판단에 사용하는 보안 식별자임

따라서 ‘Pod에 IP가 생겼다’와 ‘필요한 ipcache 정보가 올바르게 반영되었다’는 서로 다른 확인 사항임. 또한 Endpoint ID와 Security Identity를 혼동해 정책을 읽으면 안 됨.

2.3LB Map: Service와 백엔드 선택 정보를 담음

Cilium이 eBPF 기반 Service 처리를 수행하는 구성에서 LB 관련 Map은 Service frontend와 backend 등 로드밸런싱 정보를 유지하는 역할을 함. frontend는 대표적으로 Service IP·포트·프로토콜 조합으로 이해할 수 있음.

기존 L4 장비의 VIP와 백엔드 풀에 대응시킬 수 있지만, 중앙 장비 한 대를 항상 경유한다는 의미는 아님. 실제 Map은 서비스·백엔드·역변환 등 여러 구조로 나뉠 수 있음.

socket LB가 사용되는 경우에는 TCP connect() 같은 소켓 동작 시점에 목적지가 백엔드로 선택될 수 있음. 따라서 ‘Service VIP 패킷이 먼저 생성되고, 항상 tc에서 목적지를 바꾼다’고 고정하면 안 됨. 이 노트는 Cilium을 설치했다는 이유만으로 kube-proxy 대체 설정까지 활성화되었다고 가정하지 않음.

2.4Policy Map: 허용·차단 판단에 필요한 상태를 담음

Cilium은 정책과 Identity 정보를 실제 데이터 경로에서 사용할 수 있도록 반영함. Policy Map은 그 판단에 쓰이는 상태이며, 상대 Identity·방향·프로토콜·포트 등의 조건을 이해하는 것이 중요함. 아래는 실제 내부 key/value를 그대로 옮긴 표가 아니라 개념 예제임.

상대 Identity방향프로토콜·포트예시 판단
frontend 역할의 Identitybackend ingressTCP 8080허용 조건으로 정의함
허용되지 않은 역할backend ingressTCP 8080default deny가 적용되는 상황에서는 차단 대상임

중요한 전제는 정책 강제 적용 상태임. Map에서 항목 하나를 찾지 못했다는 사실만으로 모든 상황에서 반드시 차단된다고 단정할 수 없음. 정책 모드·방향·wildcard·연결 상태·추가 정책 등의 문맥을 함께 확인해야 함.

Kubernetes NetworkPolicy와 CiliumNetworkPolicy는 같은 리소스가 아님. 이번 노트의 선택 실습은 표준 Kubernetes NetworkPolicy를 사용하고, Cilium 고유의 L7·명시적 deny 정책은 별도 확장 범위로 둠.

2.5Map 조회와 패킷 처리가 연결되는 과정

아래는 Cilium이 관리하는 Linux Pod 간 통신을 설명하기 위한 역할 관계임. 특정 버전의 모든 패킷이 같은 순서로 세 Map을 한 번씩 읽는다는 뜻이 아님.

기존 연결은 연결 추적 상태를 활용할 수 있고, 로컬·원격 Pod, 터널·native routing, socket LB, L7 프록시 여부에 따라 처리 경로가 달라짐. ‘Map 세 개를 외운다’보다 ‘어떤 판단을 어떤 상태로 하는가’를 구분하는 것이 핵심임.

2.6선택 실습: Map과 반영 상태 확인

Linux Node에서 일반 BPF Map 목록 확인

조회 도구와 권한이 준비된 테스트 Node에서 사용하는 예시임.

bpftool map · bash (예시, 실행 결과 아님)
sudo bpftool map show

대상 Node의 Cilium agent 컨테이너 안에서 확인

아래 명령은 조사 대상 Pod가 있는 Node의 Cilium agent 컨테이너 안에서 실행하는 예시임. 임의의 다른 Node에서 조회한 결과를 조사 대상 Node의 상태로 간주하면 안 됨.

cilium-dbg · bash (예시, 실행 결과 아님)
# IP·Identity 등의 대응 확인
cilium-dbg bpf ipcache list

# 서비스·백엔드 관련 BPF 상태 확인
cilium-dbg bpf lb list

# 정책 관련 BPF Map 확인
cilium-dbg bpf policy get --all

실행 전 배포된 버전의 --help를 확인해야 함. 규모가 큰 환경에서는 전체 정책 Map 조회가 많은 정보를 출력할 수 있으므로 필요한 endpoint로 범위를 좁혀 확인하는 편이 좋음. 이 문서는 Map 항목을 수동으로 수정·삭제하는 명령을 포함하지 않음.

Map 용량도 운영 조건임. 공식 문서는 Map별 한도와 크기 설정을 설명하며, 연결 추적 Map 삽입 실패가 통신 장애로 이어지는 경우도 다룸. 단순히 용량을 늘리는 대신 해당 drop 사유·사용량·메모리 조건을 확인해야 함.

3Hubble & Troubleshooting

3.1eBPF Event가 Hubble Flow로 연결되는 과정

Hubble은 Cilium에서 관찰한 통신 정보를 조회할 수 있게 하는 관찰 기능임. Node의 Hubble server는 Cilium agent 안에 내장되며, Relay는 여러 Node의 Hubble API를 연결해 클러스터 범위로 조회할 수 있게 함.

이 그림은 이벤트를 전달하는 경로이지 실제 업무 패킷의 전달 경로가 아님. 업무 패킷이 Hubble Relay로 모인 뒤 전달되는 구조가 아님.

L7 관찰은 별도 구분이 필요함. HTTP 요청 같은 상세 정보는 필요한 정책·프록시 구성이 있어야 하며, 모든 HTTP·암호화 통신의 애플리케이션 내용을 eBPF가 자동으로 읽는다고 가정하면 안 됨. L7 프록시에서 발생한 관찰 정보도 Hubble에 나타날 수 있음.

3.2Hubble Flow는 전체 패킷 저장본이 아님

Flow를 읽을 때는 다음 항목을 함께 보는 것이 유용함.

  • 관찰 시각과 Node
  • 출발지·목적지 Pod 또는 IP
  • 출발지·목적지 포트와 프로토콜
  • Security Identity 등 식별 정보
  • FORWARDED, DROPPED 같은 verdict
  • drop reason 또는 TCP flag 등 원인 추적 정보
  • 제공되는 경우 HTTP 요청·응답 등 L7 정보

verdict는 해당 관찰에서 기록된 처리 판단임. Map은 ‘처리에 참고한 상태’이고 Flow는 ‘관찰된 통신 기록’이므로 서로 구분해야 함.

Hubble server는 이벤트를 사용자 공간 메모리의 순환 버퍼에 보관하며, 버퍼가 차면 오래된 이벤트를 덮어씀. 이것은 커널 BPF Map과 동일한 버퍼가 아니며, 기본적으로 무기한 감사 로그를 보관하는 시스템도 아님. 장기 보관은 별도 수집·보존 설계를 검토해야 함.

또한 한 통신이 여러 지점에서 관찰될 수 있으므로 Flow 항목 수를 그대로 사용자 요청 수나 TCP 연결 수로 계산하면 안 됨. 관찰 범위·필터·버퍼·이벤트 수집 상태를 확인하지 않은 상태에서 ‘기록이 없으니 통신도 없었다’고 단정하지 않아야 함.

3.3FORWARDED / DROPPED의 의미

관찰 내용말할 수 있는 것아직 단정할 수 없는 것
FORWARDED해당 관찰 지점에서 전달 판단이 기록됨목적지 도착·응답·업무 처리 성공
DROPPED해당 지점에서 차단·폐기가 관찰됨모든 drop이 NetworkPolicy 때문이라는 결론
Policy denied 사유정책 판단과 관련된 거부를 조사할 근거임정확히 어느 정책·방향이 원인인지의 최종 결론
조회 결과 없음해당 조회 범위에서 기록을 찾지 못함패킷이 없었거나 네트워크가 정상이라는 결론

공식 문제 해결 문서는 정책 거부뿐 아니라 잘못된 목적지 MAC이나 연결 추적 Map 삽입 실패 같은 다른 drop 원인도 구분함. 따라서 DROPPED를 발견하면 verdict 다음으로 reason과 관찰 위치를 읽어야 함.

예를 들어 요청의 출발 지점에서 FORWARDED가 보여도, 목적지 정책·외부 방화벽·애플리케이션 수신·응답 경로에서 실패할 수 있음. 정상 여부는 요청과 응답, 필요하면 애플리케이션 결과까지 연결해서 판단해야 함.

3.4Hubble로 범위를 좁히는 조회 예제

아래는 이미 Cilium·Hubble·조회 연결이 준비된 테스트 환경에서 사용하는 예시임. study-w7/backend는 예시 namespace/Pod 이름임. Deployment 이름이 아니라 실제 Pod 이름에 맞춰 바꿔야 함. 실행한 결과나 설치 절차가 아님.

hubble observe · bash (예시, 실행 결과 아님)
# Cilium·Hubble 상태와 Hubble API 접근 확인
cilium status
hubble status

# 실제 설치 버전의 조회 옵션 확인
hubble observe --help

# 대상 Pod와 관련된 관찰 정보
hubble observe --pod study-w7/backend

# 대상 Pod와 관련된 차단 정보
hubble observe --pod study-w7/backend --verdict DROPPED

# 대상 Pod와 관련된 전달 정보
hubble observe --pod study-w7/backend --verdict FORWARDED

--pod 조회는 해당 Pod와 관련된 트래픽을 좁히는 용도임. ingress/egress 정책 방향이나 요청/응답을 verdict 하나만으로 판단하지 않아야 함. 단일 Node의 API에 연결했는지 Relay에 연결했는지도 확인해야 함.

상태 확인에 실패한다면 업무 통신 장애와 Hubble의 관찰 경로 장애를 먼저 나누어야 함. Hubble API 연결 문제 때문에 결과를 못 읽는 상황을 네트워크 정책 차단으로 잘못 판단할 수 있음.

3.5NetworkPolicy 문제를 추적하는 순서

아래는 실제 장애 재현 결과가 아니라 학습용 점검 절차임. Hubble의 관찰 정보와 Kubernetes/Cilium의 설정 상태를 함께 비교하는 접근임.

  1. 대상과 시각 고정
    • 어느 namespace·Pod에서 어느 목적지의 어떤 포트로 시도했는지 기록함.
    • 장애 시각, 실제 Pod IP, 배치 Node를 확인함.
  2. 조회가 가능한 상태인지 확인
    • Hubble API 접근·Node 범위·필터 조건을 확인함.
    • 오래된 이벤트가 버퍼에서 사라졌을 가능성을 고려함.
  3. verdict와 reason 확인
    • drop이 보이면 정책 거부인지 다른 데이터 경로 오류인지 구분함.
    • 전달만 보이면 요청·응답을 나누어 마지막 관찰 지점을 좁힘.
  4. 정책이 선택하는 대상을 확인
    • podSelector, namespace, label, 포트, 방향을 확인함.
    • 출발지 egress와 목적지 ingress를 따로 확인함.
  5. 정의와 실제 반영 상태 비교
    • 정책 리소스뿐 아니라 endpoint·Identity·관련 Map 상태를 확인함.
    • 조회한 Cilium agent가 대상 Node의 것인지 확인함.
  6. 동일한 조건으로 재확인
    • 변경이 필요하면 테스트 환경에서 승인된 범위로 수행함.
    • 동일 목적지·포트의 요청/응답과 애플리케이션 결과를 다시 확인함.

기존 방화벽 운영의 ‘정책 정의 확인 → 세션·트래픽 로그 확인 → 실제 연결 재확인’과 대응시킬 수 있음. 단, Kubernetes에서는 Pod 재생성으로 주소·Node가 달라질 수 있어 대상 식별을 함께 고정해야 함.

3.6선택 실습: 정책 전후의 관찰 비교

테스트 전제

다음은 아직 수행하지 않은 실습 설계임. 운영 namespace가 아니라 별도 테스트 namespace study-w7을 사용한다는 가정임.

  • 실제 Pod 이름을 각각 frontend, backend, other로 가정함.
  • label은 각각 app: frontend, app: backend, app: other임.
  • backend가 TCP 8080에서 실제로 수신하고 있음을 별도 확인해야 함.
  • 처음에는 다른 정책과 외부 장애가 없는 통제된 조건을 가정함.
  • Cilium의 정책 강제 적용이 활성화된 조건이어야 함.
  • 아래 YAML은 NetworkPolicy 객체 전체이지만 namespace·Pod·Service를 생성하는 manifest는 아님.

정책 예제

같은 namespace의 app: frontend Pod에서 app: backend Pod의 TCP 8080으로 들어오는 연결을 허용하는 예제임.

NetworkPolicy · YAML (설명용)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-allow-frontend
  namespace: study-w7
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080

이 예제는 backend의 ingress 방향만 선택함. frontend의 egress 정책을 만들거나 DNS 허용을 추가하는 예제가 아님. 표준 NetworkPolicy에서는 여러 정책의 허용 범위가 합쳐지므로, 다른 정책이 넓게 허용하고 있다면 이 예제 하나로 다른 모든 접근이 차단된다고 말할 수 없음.

관찰할 비교 항목

아래는 실습 목표이며 실제 출력·성공 결과가 아님. 정책 외 조건이 같고 새 연결을 시도한다는 가정임.

테스트정책 적용 후 확인할 기대
frontend → backend TCP 8080허용 대상과 실제 반영 상태를 확인하고 요청·응답 관찰을 비교함
other → backend TCP 8080다른 허용 정책이 없다면 ingress 거부 관찰을 확인함
frontend → backend 다른 포트앱 수신 여부와 별개로 포트 제한이 실제 반영되는지 확인함

실습 시에는 같은 테스트를 정책 전후로 반복하고, Hubble Flow·drop reason·정책·Pod label을 함께 기록함. 이미 맺어진 연결의 상태가 비교를 흐리지 않도록 새로운 연결을 기준으로 확인하는 편이 좋음.

이 노트에서는 정책 적용·삭제, 테스트 Pod 배포, 통신 생성 명령을 실행하지 않았음. 실제 실습을 진행할 때는 namespace와 기존 정책을 먼저 확인하고, 이번 실습에서 만든 객체만 되돌릴 수 있게 정리해야 함.

3.7이번 주 내용의 연결

운영에서 중요한 것은 ‘eBPF를 쓰므로 빠르고 안전하다’는 추상적인 결론이 아니라, Program이 실행되는 위치, 판단에 필요한 상태, 관찰된 결과를 연결해 설명할 수 있는지임. FORWARDED 하나나 정책 YAML 하나만으로 통신 성공을 확정하지 않아야 함.

토론 질문 3. Hubble에서 출발지의 FORWARDED가 보이는데 애플리케이션 요청은 실패한다면, 다음으로 어느 지점과 어떤 응답 정보를 확인해야 하는가?

토론 질문 4. Hubble 조회 결과가 비어 있을 때, 통신이 없었다고 결론 내리기 전에 조회 범위·버퍼·API 상태 중 무엇을 확인해야 하는가?
